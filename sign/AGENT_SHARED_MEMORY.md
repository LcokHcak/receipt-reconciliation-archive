```

   │  桥接自动写
   ▼

团号汇总 group_code ────────┤ tour_match(团号匹配:团号∈团号表 + 购买日∈[团号起止窗口] + 代理一致)
   │ 未过→待补救(/daily/remedy)│  只有 posted + tour_match_status='matched' 的台账行能进下一步
   ▼                          ▼

   │  bill_match(P1..P6,按小票号/购买日/团号/护照/姓名)
```

## 3. 关键业务规则(改之前必须懂)

- **客人返点 = 纯卖出KRW × 客人点数**;客人点数 = 免税店基本点 + 追加点 + **扣点(deduct)**。
  扣点按桶:乐天/爱宝客 = **-0.005**、新罗 = **0**。base=0 时点数夹到 ≥0。
  计算在 `lib/monthly/customer_rebate_calculator.js` + `services/monthly/merge_streaming_service.js`。
  **netKrw 与点数来自账单**,台账只决定"哪些账单被匹配进来(覆盖率)"。
- **未收 = 账单有、台账无**(方向别搞反)。
- **派生新鲜度(6fbc306,2026-06-13)**:monthly_data/交付包 = 「已核对台账 + 最新账单 + 最新配置」的**纯派生只读**结果。`monthly_workspace.derivation_dirty_from`(tour_match<bill_match<merge,null=新鲜)记录最浅需重跑阶段:改账单/导入→bill、团号/模式→tour、扣点→merge、解决冲突/重跑行→merge(状态机 `lib/monthly_pipeline/derivation_stages`,服务 `derivation_recompute_service`)。进**最终核对页**(打开即 `ensureFresh`)/**出包**(`merged===false||derivationDirtyFrom`)时从最浅脏阶段重跑到 merge、清零;新鲜则 no-op。**monthly_data 逐行手改已下线**(PATCH `/monthly-data/:id`→410):修正一律上移台账/账单/扣点/模式,回核对页自动反映。**改返点/匹配逻辑或加新的上游变更入口时,记得 markDirty 对应阶段,否则导出会滞后。** `POST /stages/ensure-fresh` 持一把 pipeline 锁跑整段。
- **退货(refund)** = 账单负数行/冲减行。1/2/3 月源账单里普通退货经常 `客人返点金额=0/空`,但最终答案会按负净额+点数算负返点冲减,所以**普通账单退货不能盲信 raw rebate=0**;品牌活动退货/负项则使用品牌活动表里的 `客人返点金额`。退货不该卡 `missing_rebate`(`missing_rebate` 只卡匹配上的销售行 `daily_receipt_id` 非空)。
- **退货冲减归属(d1256ea,2026-06-11)**:退货行小票号命中本月 `matched` 台账小票号 = 该票已收、退货是对已收票的冲减 → merge 时带**台账客户身份**(daily_receipt_id/姓名/护照/出境日/团号)写 monthly_data(`merge_streaming_service.buildMonthlyRowFromBill` 的 `dailyRow` 参数),冲减自然进 eligible/客户汇总分组/PDF/四桶;**未命中的退货行保持 bill-only,被交付 eligible 口径排除**(那是未导入台账客户的退货,不能进交付)。stats 有 `refundLinked` 计数。背景:退货行账单上没护照,旧逻辑全写 bill-only 被排除 → 冲减丢失、客户返点虚高(BAO CHAO 买32退32再买33:系统 1,391,325 vs 答案 695,662;修复后 695,663 ✓)。**改 eligible 口径或退货路径时必须保住这条归属逻辑**。
- **品牌活动** = 源文件为 `N月品牌活动数据...xlsx`,多为无小票号/无团号,按 `姓名+护照+品牌+购买日` 等字段导入 `brand_activity`,merge 折入**乐天首尔最终数据**;不走 OCR/团号/账单匹配/未收方向,返点用表内 `客人返点金额`。
- **字段冲突** = 台账≠账单同字段 → `conflict_fields`;一票多商品**不应**误判冲突;B 类错表也进字段冲突。
- **bill_match 优先级**:P1 小票号 / P2 小票号+购买日 / P3 小票号+团号 / P4 护照+日+店 / P5 姓名+日+店(以上命中=自动匹配);**P6 模糊**=兜底,**前缀+同购买日+同护照或同姓名**才进候选,**绝不自动匹配,只生成人工待审**。

## 5. 必须知道的陷阱(本仓库特有,AGENTS.md 之外的)

1. **动态 `IN(...)` / 批量 SQL 必须分块**(≤500),否则 SQLite `too many SQL variables`。用 `chunkArray`。已修过:`bill_match_log_repository`、`daily_receipt/writes.js publishToMonthly`。**新写按 id/hash 拼 IN 的查询一律分块 + 配真实 sqlite 规模测试。**
2. **multipart 文件名乱码**:busboy 默认 latin1,中文/韩文名变 `â®®...`。统一走 `decodeMultipartFilename`(`lib/workbench_utils`)。月度导入、OCR 上传都已接。
3. ~~**两套 merge**~~ → **已合并(b181153,2026-06-13)**:`merge_service` 改为零逻辑薄壳委托 `merge_streaming_service`(生产实现)。改返点逻辑只改 `merge_streaming_service` 一处,不会再分叉。旧 5 测试 + 5 脚本经薄壳无缝转发。
4. **bill_match 候选池**:只收 `ledger_status='posted'` 且 `tour_match_status='matched'` 的台账(`isMatchableLedgerRow`);按桶运行只用本桶 `mode_folder`。所以 tour-match 不过 → 账单匹配不上(级联),不是 bill_match 的 bug。
5. **bill_match 重跑幂等 + 统计口径**:重跑/跑本桶前必须清本次 store_bill 范围内的 `bill_match_log` + `match_badcase`,并 reset 旧 daily bill_match 状态;`总账单行/billCount` 是 `store_bill` 商品/明细行,**不是按小票号压缩**。UI 主“台账匹配率/首页本月核对率”按 `matched daily_receipt / dailyCount` 算(台账是小票级,可到 100%);`matchedBillRows / totalBills` 只叫“账单明细覆盖”,是辅助指标。**不要再用 bill_match_log matched 明细行数除 daily_receipt 行数**。
6. **异步导入**:`handleImport` 建好 job 立刻回 `{job:{id,status:'running'}}`,后台跑;前端轮询 `GET /import-jobs/:id`。别改回同步(大文件会 408)。
7. **detectHeader**:收票工作簿表头在第 2 行 + 混汇总/备份页;`daily-receipt` 导入用 `detectHeader` 逐行找表头、跳过无表头工作表。
8. **splitByPurchaseDate**:`store_bill`/`daily`/`received` 按购买日拆月 + auto-open;`group_code`/`missing` 不拆。
9. **替换本桶 vs 追加文件**:替换本桶才清旧账单(store_bill + bill_match_log + 级联);追加文件不清;同文件按 row hash 去重(可能出现"导入任务在但 live_rows=0",正常)。
10. **交付 readiness**:`missing_rebate` 只卡匹配销售行;PDF 是「收款凭证」格式(留签字横线,**不放签名**);客户文件夹命名 `客户名 护照前4位`(空格)。
11. **node:sqlite 不支持嵌套事务**(见 AGENTS.md);Windows 用 `npm.cmd`;测试禁 mock SQLite。
12. **最终数据 Excel 模板不是全桶统一表头**:1/2/3 月样本按桶有差异(乐天首尔/釜山/爱宝客/新罗 V 明细列不同,且有空表头/重复表头)。写最终导出时必须走 `final_delivery_export_service` 的桶模板数组,不要回退到 `monthly_export/builders.DATA_COLUMNS` 这种通用列。

## 8. 更新协议(给所有 agent)

1. **开工前**:读「当前快照」+「陷阱」;`git log --oneline -3` 确认 HEAD;脏树不开工。
2. **干完后**:① 跑验证三件套(lint/test/git status,见 AGENTS.md)② 在「变更日志」**最上面**加一行 ③ 若部署了或改了服务器/版本,更新「当前快照」表 ④ 若发现新坑,加进「陷阱」;若解决了缺口,从「已知未决」划掉。
3. **冲突**:多 agent 并行可能撞这份文件 —— 只**追加**变更日志、**就地改**快照单元格,尽量小改动减少 merge 冲突;真撞了以 git log 真实 SHA 为准。
4. **不要**把一次性任务细节堆这里(那些进 commit message / 任务卡);这里只放"长期有用、跨 agent 要同步"的。
