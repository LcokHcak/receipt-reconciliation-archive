# 代理工作台 V2 架构设计

> 日期：2026-07-10
> 代码与服务器基线：`1b63bd5`
> 状态：供 Fabel5 实现的已确认架构
> 替代：`2026-07-10-代理工作台架构设计.md` 的批次组方案

## 1. 一句话结论

代理工作台不是新的审核台，而是按代理聚合的“客户回溯中心 + 待办中心”。它以客户档案为主实体，把团号确认、实时审核、回发和交付串成一条可定位、可回跳、可追责的工作链路。

推荐方案是：保留客户 JSON、批次 JSON 和月度库作为业务真相源，在现有 `workbench.sqlite` 中新增客户级可重建读模型，并新增独立的持久任务表；前端只消费服务端分页结果，不扫描批次、不自行推导状态。

## 2. 当前页面与真实数据结论

### 2.1 当前页面的问题

`ReviewView.vue` 中的“代理视图”仍是单批次筛选页签：

- 左栏、模式、状态均从当前批次全部 tasks 在浏览器临时计算。
- 中间仍显示护照图片，右侧仍显示 OCR 字段编辑器，和代理回溯任务无关。
- 左栏很窄，页签和筛选项挤压换行；数据量上来后会一次加载并渲染整个批次。
- 没有跨批次、跨收票员的代理视角，也没有稳定的独立 URL。
- 团号确认、审核、回发之间没有带定位信息的回跳协议。

### 2.2 `1b63bd5` 服务器证据

当前抽查批次 `batch_20260708_123821_df7532f8` 有 112 个客户组、613 个任务：

- `task.customerAgentName` 非空数为 0。
- 112 个对应 `customer.json` 全部存在代理名。
- 真实代理分布包括永乐 36、贝拉 58、韩免喜宝 9 等。

7 月生产数据量级约为：

- 客户档案 16,205 个，原图 84,256 张。
- 48 个客户库 workspace、21 个操作员、136 个代理名。
- 131 个关联审核批次。

因此不能把 task 或 sourceGroup 当成代理真相源，也不能在请求时全盘扫描 JSON。新工作台必须以 `customer.json.agentName` 为代理锚点，以批次数据覆盖审核进度。

## 3. 产品目标和边界

### 3.1 V1 必须解决

1. 按自然月查看当前用户有权看到的代理。
2. 选中代理后，查看该代理跨批次的客户、收票时间、图片数、店、模式和审核进度。
3. 明确每个客户当前最该做什么，并一键跳到对应业务页的准确位置。
4. 在右侧查看“及时发上家”和现有特殊回发任务，完成后有操作人和时间记录。
5. 支持跨月未完成任务，不能切月后消失。
6. 在 2 万客户、10 万图片规模下稳定分页，不把全部数据发到浏览器。

### 3.2 V1 不做

- 不在代理工作台中编辑 OCR 字段或审核图片。
- 不复制团号确认、待补救、回发、交付的数据写入逻辑。
- 不建立代理别名维护、权重、群聊、自动收票、AI 任务规则 UI。
- 不把历史 JSON 迁移为唯一主库，不改写历史批次来补代理名。
- 不把“及时发上家”和“给下游代理发确认回执”混成同一种任务。
- 不在 V1 直接删除审核台旧“代理视图”；先灰度对照，再下线。

## 4. 页面信息架构

独立路由：`/agents?month=2026-07&agentKey=...&mode=...&status=...`

禁止使用 `/agents/:workspaceKey`。现有 `workspaceKey` 类似 `260701-小票22`，它是客户库/收票员工作空间，不是自然月。

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 代理工作台     月份 [2026-07]  收票员(仅 admin) [全部]  刷新  去月度交付 │
├──────────────┬────────────────────────────────────┬────────────────────────┤
│ 代理 20%     │ 当前代理客户 60%                  │ 工作任务 20%           │
│ 搜索          │ 当前代理 / 当前可见全量统计        │ 紧急                    │
│               │ 模式、审核状态筛选                 │ 待处理                  │
│ 永乐     36   │ 序号 姓名 收票时间 图片 审核状态   │ 已完成                  │
│ 贝拉     58   │ 店 模式 下一步         [进入处理] │ 跨月遗留                │
│ ...           │ 服务端分页                         │                        │
└──────────────┴────────────────────────────────────┴────────────────────────┘
```

### 4.1 左栏：代理

- 显示规范化后的代理名、客户数、待处理数、异常数。
- 支持名称搜索；空代理统一为“未标代理”并计入异常。
- V1 只做字符级规范化：去首尾空格、全半角与大小写统一。
- 不按相似语义合并名称，不把“永乐”和“永乐旅行”自动当成一个代理。
- 代理多于 200 时服务端分页；当前 136 个可以默认取前 200。

### 4.2 中栏：客户组

每行必须包含：

- 序号、姓名或“待识别”。
- 收票时间，按新到旧排序。
- 原图数、有效图数、异常图数。
- 高层审核状态。
- 免税店。
- 模式。它是最醒目的业务字段。
- 下一步动作。
- “进入处理”按钮。

模式显示规则：

- 团号未确认：显示候选模式，并明确标“候选”。
- 团号已确认：使用 `sourceGroup.tourConfirm.mode`。
- 已结算：以台账/小票实际模式为准；多模式显示主模式 `+N`，任一模式均可被筛选命中。
- 绝不能把 OCR 候选模式显示为已确认模式。

### 4.3 右栏：工作任务

分为紧急、待处理、已完成三组折叠区：

- 紧急：已超时或需纠正。
- 待处理：已具备发送条件的“及时发上家”及现有特殊模式回发。
- 已完成：保留近期完成记录，默认只取最近 30 条。
- 跨月未完成任务仍显示，标明来源月份；右栏不随当前月份把旧任务隐藏。

任务完成必须记录 `completedBy/completedAt/note`，重复点击幂等。

### 4.4 刷新和 URL

- 默认 60 秒轻量刷新，另有手动刷新按钮。
- 刷新不重置当前代理、筛选、分页游标和滚动位置。
- 月份、代理、模式、状态写入 query，页面可复制链接和浏览器前进后退。
- query 非法时回退到最近有数据月份，页面提示一次，不白屏。

## 5. 三种状态必须分开

页面不能再用一个 status 同时承担三件事。

### 5.1 高层审核状态 `reviewStatus`

| 值 | UI | 口径 |
|---|---|---|
| `recognizing` | 识别中 | 原图预处理/OCR/分类仍在运行 |
| `ready_for_sync` | 待建档 | 客户已准备好但没有有效批次组关联 |
| `tour_pending` | 待确认团号 | 已进入批次，但非豁免客户尚未确认团号 |
| `review_pending` | 待审核 | 团号可用，仍有必审图片未完成 |
| `rephoto` | 需重拍 | 任一必需图片被判定重拍 |
| `needs_remedy` | 待补救 | 结算/桥接进入待补救 |
| `needs_confirm` | 待人工确认 | 模糊或业务冲突需人工处理 |
| `passed` | 已通过 | 必审图片完成且 group `settlementStatus=settled` |

状态优先级固定为：`rephoto > recognizing > ready_for_sync > tour_pending > review_pending > needs_remedy > needs_confirm > passed`。若一个客户同时命中多个异常，列表显示最高优先级，详情返回全部 `reasonCodes`。

### 5.2 主流程下一步 `nextAction`

| reviewStatus | nextAction | 跳转 |
|---|---|---|
| `recognizing` | 查看识别进度 | 实时队列定位客户组 |
| `ready_for_sync` | 建档同步 | 当前批次/客户库入口 |
| `tour_pending` | 确认团号 | 团号确认站定位客户组 |
| `review_pending`/`rephoto` | 审核/重拍处理 | 实时审核定位客户组 |
| `needs_remedy`/`needs_confirm` | 处理补救 | 月度待补救定位客户 |
| `passed` | 查看记录 | 审核只读定位或客户库 |

### 5.3 操作任务 `workflowTask`

“及时发上家”是运营动作，不等于审核状态，也不等于团号确认回执。

- 非豁免且有小票的客户，在团号确认后才创建 `send_upstream` 任务。
- 团号未确认前，中栏只显示“等待团号确认”，不生成可完成的假任务。
- 无小票、业务豁免客户不创建 `send_upstream`。
- send12/send17/send18/S 活动继续作为特殊 task subtype。
- 团号撤销时，未完成任务自动取消；已完成历史不删除，而是生成“需复核/纠正”任务。

## 6. 数据真相和读模型

### 6.1 真相源

| 数据 | 真相源 | 用途 |
|---|---|---|
| 客户身份、代理、收票员、原图、收票时间 | `customer_library/**/customer.json` | 客户锚点 |
| OCR、审核、团号确认、模式候选/确认、结算状态 | `storage/batches/**/batch.json` | 审核覆盖层 |
| 月度待补救、匹配、交付 | `monthly.sqlite` | 月度业务结果 |
| 新运营任务状态 | `workbench.sqlite.workflow_task` | 持久任务真相 |
| 代理工作台查询行 | `workbench.sqlite.agent_workspace_customer` | 可重建读模型 |

`agent_workspace_customer` 不是新业务主库。它损坏后可由客户 JSON + 批次 JSON 重建。

### 6.2 自然月口径

- 以 `customer.createdAt` 按 `SIGN_BUSINESS_TZ` 转换出的 `YYYY-MM` 为准。
- `createdAt` 缺失时仅可用 customerId 日期作为降级，并记录 warning。
- 禁止解析 `workspaceKey/monthKey` 得出自然月。

### 6.3 读模型表

建议表 `agent_workspace_customer`：

```sql
CREATE TABLE agent_workspace_customer (
  customer_pk TEXT PRIMARY KEY,
  calendar_month TEXT NOT NULL,
  workspace_key TEXT NOT NULL,
  customer_id TEXT NOT NULL,
  owner_user_id INTEGER,
  owner_username TEXT,
  agent_key TEXT NOT NULL,
  agent_name TEXT NOT NULL,
  customer_name TEXT,
  received_at TEXT NOT NULL,
  original_image_count INTEGER NOT NULL DEFAULT 0,
  valid_image_count INTEGER NOT NULL DEFAULT 0,
  abnormal_image_count INTEGER NOT NULL DEFAULT 0,
  batch_id TEXT,
  group_key TEXT,
  monthly_workspace_key TEXT,
  store_keys_json TEXT NOT NULL DEFAULT '[]',
  candidate_modes_json TEXT NOT NULL DEFAULT '[]',
  confirmed_modes_json TEXT NOT NULL DEFAULT '[]',
  review_status TEXT NOT NULL,
  next_action TEXT NOT NULL,
  reason_codes_json TEXT NOT NULL DEFAULT '[]',
  settlement_status TEXT,
  projection_version INTEGER NOT NULL,
  projected_at TEXT NOT NULL,
  UNIQUE(workspace_key, customer_id)
);
```

索引至少覆盖：

- `(calendar_month, owner_user_id, agent_key, received_at DESC, customer_pk DESC)`
- `(calendar_month, owner_user_id, review_status)`
- `(calendar_month, owner_user_id, received_at DESC)`

`customer_pk` 必须是 `workspaceKey + customerId` 的稳定组合，不能假设 customerId 全局唯一。

`monthly_workspace_key` 只能来自台账桥接/结算实际落入的月度工作区。它与客户库 `workspace_key` 是两个概念；尚未桥接时允许为空，禁止根据 `260701-小票22` 之类名称猜测。

### 6.4 持久任务表

```sql
CREATE TABLE workflow_task (
  id TEXT PRIMARY KEY,
  task_key TEXT NOT NULL UNIQUE,
  calendar_month TEXT NOT NULL,
  workspace_key TEXT NOT NULL,
  customer_id TEXT NOT NULL,
  batch_id TEXT,
  group_key TEXT,
  agent_key TEXT NOT NULL,
  task_type TEXT NOT NULL,
  subtype TEXT,
  status TEXT NOT NULL,
  priority INTEGER NOT NULL DEFAULT 0,
  due_at TEXT,
  payload_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  created_by TEXT,
  completed_at TEXT,
  completed_by TEXT,
  cancelled_at TEXT,
  cancel_reason TEXT,
  source_version INTEGER NOT NULL DEFAULT 1
);
```

`task_key` 使用确定性幂等键，例如 `send_upstream:<workspaceKey>:<customerId>:<tourConfirmVersion>`。重试、批次重复保存和后台修复不能生成重复任务。

### 6.5 双层增量投影

1. 客户创建/保存时调用 `upsertCustomerAnchor(customer)`，写代理、owner、时间、原图数。
2. 批次保存时调用 `upsertReviewOverlay(batch)`，只覆盖审核、团号、模式、结算字段。
3. task 中空代理名绝不能覆盖客户锚点的代理名。
4. 客户删除时删除读模型行，并取消未完成运营任务。
5. 投影失败不能阻断客户/批次主写入，但必须记录结构化日志和待重试项。
6. 启动后台 reconciler 修复漏投影；不得在 API 请求时退化为全盘扫描。

## 7. API 契约

统一前缀：`/api/agent-workspace/v1`。

### 7.1 概览与代理

- `GET /summary?month=2026-07&ownerUserId=`
- `GET /agents?month=2026-07&search=&ownerUserId=&limit=200&cursor=`

summary 同时返回 `selectedAgent` 和 `visibleAll` 两组数字：总客户、待审核、已通过、未完结、今日新增、异常。统计分母必须始终是当前权限 + 当前月 + 当前 owner 筛选后的客户。

### 7.2 客户分页

`GET /customers?month=&agentKey=&mode=&reviewStatus=&ownerUserId=&limit=50&cursor=`

- 游标为 `(received_at, customer_pk)`，不使用 offset。
- mode 对多模式客户采用“任一模式命中”。
- 响应包含 `nextCursor`，不返回完整 task/OCR payload。
- 非法 limit 最大钳制为 100。

### 7.3 任务

- `GET /tasks?agentKey=&month=&status=&includeCarryover=true&limit=50&cursor=`
- `POST /tasks/:id/complete`

complete 接受 `note` 和可选 `expectedVersion`，重复完成返回当前结果，不重复写事件。无权限、任务已取消、版本冲突分别返回 403、409、409。

### 7.4 维护端点/脚本

投影重建优先做 CLI，不暴露普通用户 API：

```bash
node scripts/rebuild_agent_workspace_projection.js --dry-run
node scripts/rebuild_agent_workspace_projection.js --apply
```

输出各月客户数、代理数、缺客户/缺批次、重复 key、状态分布和耗时。`--apply` 必须在事务中换表或按 version 重建，失败保留旧可用索引。

## 8. 权限与数据隔离

- admin/finance：可见全局；finance V1 只读，不能完成任务。
- reviewer：沿用 `operator_scope`，只看 `ownerUserId/ownerUsername` 属于自己的客户与任务。
- admin 页面提供低强调度的“收票员”筛选；reviewer 不显示该控件。
- summary、代理计数、客户列表和任务列表必须使用同一个 scope builder。
- 前端传 `ownerUserId` 不能扩大权限；服务端先算最大可见 scope，再收窄。
- deep link 打开审核页时仍由目标页面重新验权，代理工作台的可见不代表自动授权。

## 9. 与现有四个业务页面的联动

### 9.1 团号确认站

`/review/:batchId?view=confirm&group=<groupKey>&returnTo=<localPath>`

- `ReviewView` 根据 `view=confirm` 初始化页签。
- `TourConfirmPanel` 接收并选中 `groupKey`，无效时提示“客户组已变化”而不是静默选第一组。
- 确认完成后可返回代理工作台原代理、月份和筛选位置。

### 9.2 实时审核

`/review/:batchId?view=queue&group=<groupKey>&returnTo=<localPath>`

- 进入后自动定位该客户组的第一张未处理图片。
- 若全部完成，进入只读概览，不跳到其他客户。

### 9.3 回发

`/review/:batchId?view=sendback&task=<taskId>&returnTo=<localPath>`

- 旧 sendback panel 在过渡期由 workflow task adapter 提供数据。
- 特殊回发仍在原页处理，代理工作台只做任务列表和准确跳转。

### 9.4 待补救与交付

- 待补救链接使用该客户实际 `monthly_workspace_key`，并携带 customerId、tourNo 或 groupKey 供目标页筛选。尚未产生月度工作区时按钮显示“尚未进入月度工作区”，不得把客户库 workspaceKey 填进 `/daily/remedy/:workspaceKey`。
- “去交付”进入现有月度交付，不在代理工作台生成包。
- 单代理交付筛选若后端当前不支持，V1 只带 month，不伪造“已按代理过滤”。

所有 `returnTo` 只接受站内相对路径，并校验允许前缀，防止开放重定向。

## 10. 旧回发队列迁移

现有 `storage/sendback_queue.json` 是单文件整读整写，只适合少量特殊回发，不适合 1.6 万客户通用任务。

迁移策略：

1. 新建 workflow task repository 和幂等迁移脚本。
2. 将旧 pending/done/cancelled 项映射为新 task，保留原 ID、时间、操作人和 payload。
3. 旧 `/sendback-queue` API 暂时通过 adapter 读取新表，仅返回旧 UI 认识的 subtype。
4. 双写不允许长期存在；切换后旧 JSON 只读归档。
5. 对比新旧状态计数完全一致后，才让旧面板读新表。

## 11. 历史回填与异常处理

### 11.1 回填顺序

1. 流式遍历每个 `customer.json` 建锚点，不一次加载全部客户。
2. 使用 `customer.review.lastBatchId/lastSourceGroupId` 叠加当前有效审核状态。
3. 扫描批次仅补关联与校验，不用旧历史 group 覆盖客户当前状态。
4. 迁移旧 sendback queue。
5. 输出 parity 报告后原子启用 projection version。

### 11.2 边界规则

- 客户存在、批次不存在：`ready_for_sync`，不丢行。
- 批次存在、客户不存在：记录 orphan，不在正常代理列表显示。
- 同一客户多个活动批次：优先 customer.review 指向；否则按批次更新时间，并记 `multiple_active_batches`。
- 代理后来更名：客户保存触发更新；V1 不自动合并历史别名。
- 团号确认后又撤销：取消 pending task；done task 留审计并建 correction task。
- 客户跨月重审：归属月不变，工作任务可跨月显示。
- OCR 重跑：不改变 receivedAt、agent、owner 和任务完成历史。
- 投影落后：API 返回 `projectionLag` warning；不返回未经权限过滤的 JSON 扫描结果。

## 12. 性能、可观测和备份

以 20,000 客户、100,000 图片、200 代理、250 批次压测：

- summary/agents/customers/tasks API P95 小于 300ms。
- 客户第一页响应小于 200KB。
- 浏览器 DOM 客户行不超过当前页；默认 50。
- 重建脚本峰值内存小于 512MB，可中断重跑。

日志至少记录：projection upsert 失败、reconciler 修复数、孤儿关联、任务幂等冲突、API 耗时。`readyz` 不应因可重建读模型短暂落后直接判应用不可用，但应暴露 degraded detail。

`workbench.sqlite` 已在数据库备份范围内；新增 workflow task 后必须确认备份与恢复测试覆盖该表。读模型可重建，任务表不可当作可随意删除的缓存。

## 13. 方案比较

### A. 扩展当前 AgentQueuePanel

改动少，但仍只看单批次、依赖空 task agent、浏览器全量聚合。否决。

### B. 每次请求扫描 customer/batch JSON

短期能看到正确代理，但 1.6 万客户和并发审核下延迟不可控，权限与口径容易分叉。否决。

### C. 客户锚点读模型 + 持久任务表

读性能稳定，真相源不动，支持跨批次、跨月、审计和重建。采用。

## 14. 发布与回滚

1. 先上线表结构、投影和 shadow API，不加导航。
2. 服务器 dry-run 回填并生成 parity 报告，确认客户总数、代理分布和权限分布。
3. 启用独立 `/agents` 页面；审核台旧页签改名“本批次按代理”用于对照。
4. 观察至少一个真实工作日：投影漏写、跨月任务、深链和权限均正常。
5. 再删除旧页签，不删除团号确认/实时队列/回发。

回滚只关闭新导航/API 并恢复旧 adapter；不回滚客户/批次真相源。任务表迁移后即使页面回滚也必须保留，不允许丢完成记录。

## 15. 上线验收

- 服务器当前 7 月客户数与读模型 customer anchor 数一致；缺失项有逐条原因。
- 抽查永乐、贝拉等代理与 customer.json 数量一致，不再全部显示未标代理。
- reviewer 看不到其他 20 个操作员的数据；admin 总数与全局一致。
- 从客户行进入团号确认、实时审核、回发、待补救均定位到同一客户，返回后筛选不丢。
- 同一批次保存 10 次不重复创建任务；团号撤销边界符合第 11 节。
- 旧回发迁移前后 pending/done/cancelled 数量一致。
- 20k 压测达标，Playwright 在 1366x768 和 1920x1080 无重叠、无整页全量渲染。
