## 〇、先说三句结论

1. **你的方向是对的**:把"切图"从**不可逆的物理操作**降级成**可修正的标注**,
   这是这类问题的正解。切坏了没法回头,框标错了随时能改。

2. **但方案里有一处会出大事**:如果一张原图上 3 张票 → 3 个任务都指向同一张原图,
   **交付包会出现 3 个不同票号的文件、内容却是同一张含 3 张票的整图**。
   上家收到的等于同一张照片被当成三笔交易交了三次。这是必须先解决的。
   解法在第四节:**框是数据,裁剪是渲染** —— 把裁剪从"识别时"推迟到"交付时"。

3. **现成件比你想的多**。下面这些已经在跑了:

   | 你想要的 | 现状 |
   |---|---|
   | 字段框 + 快速定位 | ✅ **已完整实现**(`ImageViewer.vue`,带显隐开关、大小三档、记忆偏好) |
   | 同图补一张票、信息不漏 | ✅ **已实现**(`POST /tasks/:id/manual-receipt`,新任务指向同一张图) |
   | 不切图、整图直通 | ✅ **已实现**(`store_profiles.split:'none'`,乐天百货/新世界/现代百货在用) |
   | 切片回看原图 | ✅ **已实现**(`GET /tasks/:id/original-image`,能从切片回溯到 `_original`) |
   | 按店重切 | ✅ **已实现**(`POST /tasks/:id/resplit`) |
   | **整图上显示"识别出了哪几张票"** | ❌ **缺这个** —— 只有字段框,没有文档框 |
   | 框可拖拽调整 / 手动画框 | ❌ 没有 |

   **也就是说:真正缺的不是一整套新架构,而是"文档级框"这一块,加上把已有零件串成一条顺手的流程。**

## 一、现在到底是怎么坏的

### 现状链路

```
原图 (客户库 images/)
  └─ qwen 一次调用:同时给出 切图bbox + 分类 + 字段
       ├─ 0/1 个文档 → 不切,整图一条任务
       ├─ ≥2 个文档 → **按 bbox 物理裁剪**,每片一个文件、一条任务
       │                 原图另存 `_original.*`(刻意排除在批次外)
       └─ 百货(split:'none') → 强制不切,整图一条任务
```

### 你说的两种坏法,根因不同

**坏法 A:少切了(3 张票只识别出 2 张)**

- 系统只会产出 2 条任务。第 3 张票**从来没有存在过** —— 不是审核时看不见,是压根没有那条记录。
- 现有兜底:`suspect_uncut_wide`(整图明显横宽却只识别出 1 个文档 → 标转人工)、
  漏切二次调用(单张小票框过宽 → 裁出来重调一次)、
  `dept_multi_receipt_suspect`(百货整图里数出 ≥2 个不同交易号 → 标红转人工)。
- **兜底都是"标红让人看",没有一个能自动把第 3 张找回来。** 找回来只能靠人。

**坏法 B:切碎了(一张票被切成好几片)**

- 产出的碎片各自成任务,字段大多识别不出来 → 一堆待处理的垃圾任务。
- 现有兜底:bbox 退化(过小)→ 跳过不产片;`other` 区照样裁出但强制转人工。
- **代价是审核队列被垃圾撑大**,操作员要一个个删。

### 为什么切图这件事本身很难做对

- 小票是**长条形、边缘不规则、常有重叠**;手机拍摄有透视和旋转
- 模型给的 bbox 是"它以为的边界",而"两张挨着的票"和"一张长票"在像素上极难区分
- **一旦裁下去就不可逆**:裁错了,原始的空间关系就没了,人也无从判断"这块是不是另一张票的一半"

**这就是你直觉的来源,也是它正确的原因**:难点不在"框得准",在于**框错了没有退路**。

## 二、评估你的方案

### 逻辑上成立的部分(占大头)

| 你的主张 | 评估 |
|---|---|
| 不物理切图,用框表示 | ✅ **对**。把不可逆操作变成可修正的数据 |
| 高亮框便于回找 | ✅ **对**,而且这是"少切了"唯一可靠的发现方式 —— 人看着整图,一眼能看出"这块没被框" |
| 识别大了就补一张票、用同一张原图填信息 | ✅ **对**,而且**这个能力已经有了**(同图补小票) |
| 字段也加框、快速定位 | ✅ **对**,而且**已经实现了** |
| 框不要遮盖信息 | ✅ **对**,这是个真问题,见第五节的具体做法 |

### 会出事的部分(必须先解决)

**问题:交付包按票号出图,一图多任务 = 同一张照片被当成多笔交易交出去**

现在交付包是这么出的:

```js
// 乐天百货 / 新世界 / 现代百货
files.push({ dir, baseName: receiptNo, sourcePath: 那条任务的图 })
// 免税店模式桶
files.push({ dir, baseName: `${folderBase}_小票${idx}`, sourcePath: 那条任务的图 })
```

如果 3 条任务都指向同一张原图,上家会收到:

```
1042-4829.jpg   ← 三张票的合影
1042-4830.jpg   ← 同一张合影
1042-4831.jpg   ← 同一张合影
```

**这是对外交付,不是内部界面。上家会认为我们在重复报账。**

> 补充说明:乐天百货现在能"整图直通",是因为那种版式本来就是
> **一张照片 = 一张小票 + 一本护照 = 一笔交易**,一图一票。
> 而你说的场景是**一图多票**,性质完全不同,不能照搬。

**问题的另外三面:**

- **护照打码**按 bbox 涂黑。整图多票时,遮罩位置要跟着重算,现有面积闸(3%~75%)口径也要重定
- **签名/回执**按任务贴图,同图多任务会重复贴
- **审核体验**:三条任务点开是同一张大图,不放大就看不清各自那块;
  切片模式下"小票切片默认放大 350% 居中"这个优化会失效

## 三、三种可选路线

### 路线甲:全面改框选(你的原方案)

不再物理切图,一切用框表示。

- 优点:概念最干净
- 代价:**31 处依赖 `sourceImagePath` 指向"就是这份单据的图"** —— 交付包(4 个)、
  打码、签名、客户数据包、导出计划引擎、台账桥…全要重新定义
- 风险:大改交付链,而交付链是对外的,出错直接影响上家
- 判断:**不推荐一次到位**。目标对,但一步跨过去风险太集中

### 路线乙:只加框、切图照旧

在现有切片流程上叠加框显示,方便回找。

- 优点:几乎零风险
- 代价:**没解决根本问题** —— 切坏了还是切坏了,框只是让人早点发现
- 判断:**可以作为第一步,但不能是终点**

### 路线丙(推荐):框是数据,裁剪是渲染 —— 把裁剪推迟到交付时

**核心思路一句话:审核期间只有原图 + 框;要出交付包时,才按(可能被人改过的)框现裁。**

```
原图(唯一真相)
  ├─ 识别 → 产出文档框 [{type, bbox, fields}] ,**不落切片文件**
  ├─ 审核 → 人在原图上看框:框漏了就画一个、框大了就拆、框错了就拖
  │          每个框 = 一条任务(和现在一样,不改审核心智)
  └─ 交付 → 按每条任务**最终确认的框**裁一份图,命名照旧
             ↑ 这一刻才产生"一票一图",下游 31 处一个字都不用改
```

**为什么这条路能同时解决三件事:**

1. **切坏了能改** —— 框是数据,随时能拖能加能删,原图始终在
2. **交付不受影响** —— 下游拿到的仍然是"一票一图",契约不变
3. **改错了能回滚** —— 原图没动过,重新裁一次就行;现在切坏了要重传

**和你原方案的唯一区别**:交付那一刻仍然裁。
你想的是"完全不裁",但对外交付必须一票一图,所以**裁不能取消,只能推迟**。
推迟之后,裁剪就从"识别时的一次性赌博"变成"交付时按已确认数据的确定性渲染"。

## 四、路线丙的分期设计

刻意设计成**每期独立可用、可随时叫停**,不是一个必须做完才见效的大工程。

### 第 1 期:整图上显示文档框(纯增量,零风险)

**做什么**

- 后端:`buildTaskFieldRegions` 旁边加一个 `buildTaskDocRegions(task, batch)` ——
  把**同一张原图下所有兄弟任务的框**都算出来(不只当前这条),标出哪个是当前任务
- 前端:`ImageViewer` 已有字段框渲染层,复用它加一层"文档框";
  「查看原图」时显示全部兄弟框,当前任务的框高亮、其余淡显

**立刻能解决什么**

- 操作员在原图上一眼看出**哪块没被框住** → "少切了"从"永远发现不了"变成"一眼看见"
- 点淡显的框可跳到那条兄弟任务 → 回找

**不解决什么**:框还是不能改。这一期只做"看得见"。

**数据基础**:切片任务上已有 `detectionBox`(或 `modelMeta.bbox`),
百货合并档有 `modelMeta.passportBbox`(0729 补的)。**不用重跑识别。**

---

### 第 2 期:在原图上手动加一个框 = 补一张票

**做什么**

- 前端:原图上拖拽画框 → 调 **已有的** `POST /tasks/:id/manual-receipt`,
  额外把画的 bbox 一起传上去
- 后端:`createManualReceiptTaskFromSource` 多存一个 `manualBbox`
  (它现在已经复制 `sourceImagePath` 和 `sourceOriginalPath`,把框存上即可)

**立刻能解决什么**

- 坏法 A(少切了)**闭环**:看见没被框的那块 → 拖一个框 → 出一条新任务 → 填字段
- 你说的"以那个原图再填信息、保证信息不漏"**正式成立**

**注意**:这一期之后,那条新任务在交付时**必须**按 `manualBbox` 裁 —— 否则就撞上第二节那个问题。
所以第 2 期和第 3 期要一起上线,或者第 2 期先只允许在 `split:'none'` 的店用。

---

### 第 3 期:交付时按框裁(关键的一期)

**做什么**

- 新增 `lib/delivery_crop.js`:给定原图 + 归一化 bbox → 产出裁片(sharp,已有依赖)
- 四个交付服务在 `resolveTaskFile()` 之后加一步:
  **任务带框 → 现裁一份临时文件;任务不带框 → 照旧用原文件**
- 裁片写在导出的临时工作目录里,导出完随 `cleanup()` 一起删,不落长期存储

**为什么风险可控**

- **默认不变**:没有框的任务(= 今天所有任务)走原路径,行为一模一样
- 只有"新流程产生的、带框的任务"才走新路径 → 灰度天然成立
- 交付包结构、命名、目录一个字不改

**必须配套的护栏**(按 0729 定的判据):

- 裁剪失败 → **不能静默用整图顶上**(那正是第二节的灾难)。要么阻断,要么进
  「导出说明.txt」的【源图取不到·没进包】段,让人看得见
- 框面积闸:太小/太大一律拒绝并转人工(复用 `passport_mask.plausibleBbox` 的思路)
- 裁片必须验证真的写出来了、尺寸合理,再进包

---

### 第 4 期:框可拖拽修正 + 拆框

**做什么**

- 已有框可拖角调整;一个框拆成两个(切碎的反向操作:两个碎片合并)
- 改过的框标 `bboxSource: 'manual'`,交付时优先用人改的

**为什么放最后**:它是体验优化。第 1–3 期做完,坏法 A/B 都已经有解;
这一期让"改"比"删了重来"更省事。

---

### 第 5 期(可选):识别侧不再物理切图

- `split` 增加一档 `'boxes'`:只出框不落文件
- 老数据(已有切片)照旧工作,新数据走框
- **只有前四期在生产上稳了才做这一期**

## 五、"框不要遮盖信息"的具体做法

这是个真需求,而且现有字段框已经踩过一半的坑(有大小三档 + 显隐开关,就是为这个)。
建议规则:

1. **只描边不填充**。任何半透明填充在小票这种密集文字上都会降低可读性
2. **描边画在框外侧**(`outline` 而非 `border`),不占框内像素
3. **标签不压在框里**:文档框的类型标签(小票/护照)放在框**外**的角上,
   有空间放外面就放外面,没空间才放里面并加背景
4. **默认只描边、不显示标签;悬停才出标签** —— 静止时画面尽量干净
5. **「聚焦」模式**:悬停某个框时,**把框外区域压暗**而不是把框内加亮 ——
   信息区始终保持原始像素,不被任何东西覆盖
6. **一键全隐**:沿用字段框现有的显隐开关和 localStorage 记忆,别再造一个
7. 颜色遵循全站硬规则:蓝=可点击、红橙=要处理、灰阶=其余;
   **当前任务的框用蓝,兄弟框用灰,有问题的框(面积可疑/字段缺)用红橙**

## 二、"交付带框不裁"评估

### 工程上:比裁更便宜,机器现成

烧图管线**已经在生产跑** —— 护照打码就是它:

```js
sharp(sourcePath).rotate()
  .composite([{ input: 那段SVG, left, top }])
  .jpeg({ quality: 90 }).toFile(destPath)
```

EXIF 转正、bbox 外扩防贴边、面积闸、失败返回 `{masked:false, reason}` 不静默 —— 全都有。
**把黑色矩形换成一个空心框,就是换一段 SVG 字符串。** 工程量几乎为零。

### 业务上:代价随"一图几票"急剧变化

| 场景 | 占比 | 带框不裁的效果 |
|---|---|---|
| 1 票/图 | 86.8% | **完全没问题**(今天就是整图) |
| 2 票/图 | 8.7% | 可接受,上家一眼能分辨 |
| 3 票/图 | 3.8% | 开始难受:同一张照片交 3 次 |
| ≥4 票/图 | 0.7% | **明显不行**;9 票那张会交 9 份几乎一样的大图 |

**具体代价:**

- **包体积**:受影响那 26.9% 的文件从"切片"变成"整图",整图比切片大,
  粗估这部分涨 2~3 倍 → 整包大概 +40~60%。而交付包是**永久存档到 COS 的**
- **上家的活变重**:他们按文件名(交易编号)取图。现在打开就是那张票;
  改成整图后,得先找框、再看框里那张。**他们是不是接受,只有你知道**
- **打印场景更差**:整图打出来,目标票只占一小块
- **框略歪就有歧义**:裁片是"这就是那张票",带框是"框住的才是",框偏一点就可能读错

---

## 三、推荐:裁 + 外扩 + 框(三者一起,不是二选一)

你担心的其实不是"裁"本身,而是 **"裁坏了会丢信息"**。那就把这个担心直接消掉:

```
交付时:按框裁,但四周多留 15% 余量,并在裁片上把目标框描出来
```

| 你的担心 | 这样怎么消掉 |
|---|---|
| 框小了,票被切掉一半 | **外扩 15%**,框略小也能把整张票包进来 |
| 框大了,带进隔壁半张票 | 隔壁确实会露出来,但**框描出了目标**,上家不会认错 |
| 完全不裁,信息一定不丢 | 外扩后同样不丢 —— 丢信息的是"裁得紧",不是"裁" |
| 上家怎么知道是哪张 | 框标出来了,比纯裁片更明确 |

**同时保住:**
- **一票一图**(上家工作流一个字不用改)
- **包体积不涨**(甚至更小,裁片比整图小)
- **下游 31 处依赖不动**

**这比"完全不裁"和"紧裁"都好**:紧裁会丢信息,不裁会让上家收到 N 张同样的大图,
**外扩裁 + 框**两头的毛病都没有。

---

## 四、真正的设计要点:渲染方式是**配置**,不是架构

不管你最后选哪种,交付那一步都应该长这样:

```js
// 新增 lib/delivery_render.js —— 一个纯粹的"按框出图"函数
renderDeliveryImage({
  sourcePath,        // 原图
  box,               // 归一化 bbox(可能是人改过的)
  mode,              // 'crop' | 'crop-marked' | 'box-only' | 'whole'
  padRatio,          // 外扩比例,默认 0.15
  destPath,
})
```

- `crop` —— 紧裁(≈ 今天的切片)
- `crop-marked` —— **外扩裁 + 描框(推荐默认)**
- `box-only` —— 整图 + 描框(**你问的这个**)
- `whole` —— 整图不描框(1 票/图 时自动落到这里)

**为什么做成配置而不是定死:**

1. `store_profiles.js` **本来就是按店配交付方式的**(`split`、`delivery`、`exportMap` 都在里面),
   多一个 `deliveryRender` 完全顺理成章
2. 不同上家要求可能不同 —— 乐天百货要的和新世界要的可以不一样,**不用为此改代码**
3. **可以按"一图几票"自动降级**:1 票/图 → `whole`(和今天完全一致);
   2 票 → `box-only`;≥3 票 → `crop-marked`。既尊重你的偏好,又避免 9 票那种下限
4. **最重要的**:它把"crop 还是 box"从一个**必须现在拍板的架构决定**,
   降级成一个**随时能改的开关**。先按推荐值上线,上家有意见改配置即可

# 再追加(同日):两条硬约束确定后的最终形态

## 〇、你补充的两条

1. **审核台:整图 + 框,不裁剪**
2. **交付:必须是单小票切好的;可以带上隔壁票一点,但画面里不能出现两张完整的小票**

**这两条把架构唯一确定了,不用再选路线。** 前文的"路线甲/乙/丙"作废,答案就是:

```
识别 → 只出框,不落切片文件
审核 → 整图 + 框(你要的状态)
交付 → 按框裁 + 自适应外扩(唯一产生切片的地方)
```

这正是路线丙,但**审核侧也不裁了** —— 比我原来写的更彻底,而且更简单:
**全系统只剩交付这一处会裁图。**

同时**前一节"外扩 15%"的推荐作废** —— 生产实测 75% 的多票图框间距 <2%,固定外扩没有空间。
但你这条"可以带一点"救活了它:**外扩不需要避开隔壁票,只需要不让隔壁票完整入镜。**
这是个**宽松得多、而且可计算**的条件。

---

## 一、交付裁剪规则(你那句话的可执行版)

对每条任务的框 `B`,同图的兄弟框记作 `S₁..Sₙ`:

```
每条边独立算外扩量:
  想扩 = 15%(给足余量,防框略小把票切掉)
  但朝着某个兄弟框 Sᵢ 扩时,最多扩到 Sᵢ 的中线为止
  → 保证 Sᵢ 至少有一半被切掉 = 它绝不可能"完整出现"
```

| 场景 | 结果 |
|---|---|
| 那一侧没有兄弟框 | 扩满 15% |
| 那一侧有兄弟框、离得远 | 扩满 15%(还没够到中线) |
| 那一侧兄弟框贴着 | 自动缩到中线,**带一点、不带全** |
| 兄弟框和本框重叠 | 中线在本框内 → **不扩**,紧裁 |

**为什么用"中线"而不是"边缘"**:
用边缘只能保证不越界,遇到重叠就无解;用中线,**无论框怎么摆都有确定答案**,
而且"最多带隔壁半张"天然符合你说的"带上一点"。

---

## 二、必须有的护栏(这条最重要)

规则再好也可能被坏框绕过。所以交付出图后要**验一遍成品**:

```
裁出来的矩形,是否完整包含了任何一个兄弟框?
  是 → 这张图违反了"不能出现两张完整小票"
      → 不许进包。阻断 + 写进「导出说明.txt」
  否 → 放行
```

**这是可计算的验收条件,不是靠人眼抽查。** 而且它符合 0729 定下的判据:
**算出了问题必须让人看见,不能静默出图。**

对照今天修的那一整天 bug:如果没有这道闸,坏框会**静默产出一张含两张完整票的图**发给上家,
而这正是你这条硬要求要防的事。**规则负责大多数情况,护栏负责兜住剩下的。**

---

## 三、那 29.6% 框重叠的组怎么办

实测 808 个多票组里 **239 组框相互重叠**(最极端的一个,一个框吃掉另一个 52%)。
重叠分两种,处理不同:

| 类型 | 判据 | 处理 |
|---|---|---|
| **票本身挨着/叠着** | 轻微重叠 | 中线规则正常处理,能出图 |
| **框本身就错了**(一个框套住另一个) | 小框被吃掉 ≥50% | **外扩规则救不了** —— 紧裁也会带出完整的隔壁票 |

第二种**只能靠改框**,这就是「自己画框 / 拖拽调框」的真正用武之地 ——
它不再是"锦上添花的小功能",而是**这条路能不能走通的必要零件**。

而且第二种是**可以提前算出来的**:识别完就能标"这组框有严重重叠,要人看一眼",
不用等到交付才发现。

> 我原本要量"239 组里有多少是第二种",被打断了。这个数**放到第 1 期开头量** ——
> 它决定人工改框的工作量有多大,是排期的关键输入。

# 三追加:一个框罩住两张票,人工补票之后怎么交付

## 〇、先说结论:**"加一张小票"这个操作本身是错的,正确的是"拆框"**

你问的"怎么判断新加的是哪个小票",在**加票**这个操作下**无解** ——
因为加票只产生了一条任务,没产生任何"它是哪一块"的信息。

但换成**拆框**,这个问题**根本不存在**:

> **框就是身份。** 新任务是"你框住的那一张",不需要判断。

---

## 一、为什么"加票"会在交付时崩

原图有 A、B 两张票,模型只给了**一个罩住两张的大框**:

```
现在:  [任务1: 框=A∪B, 字段=??]
加票后:[任务1: 框=A∪B, 字段=??]  [任务2: 无框, 字段=人工填]
```

两个问题:

1. **任务 2 没有框** → 交付时不知道裁哪块(今天的 `createManualReceiptTaskFromSource`
   只复制 `sourceImagePath`,不带任何区域信息)
2. **就算给任务 2 补上 B 的框,任务 1 的框还罩着 A∪B** →
   任务 1 裁出来会**完整包含 B** → **撞上"不能出现两张完整小票"的护栏,直接被拦**

**所以加票之后系统处在一个交付闸门会拒绝的状态。** 必须把原框也改小 ——
那本质上就是拆框,只是分两步做、中间还留了个坏状态。

---

## 二、正确形态:拆框(一次原子操作)

```
拆之前: [框: A∪B] ── 任务1
拆之后: [框: A] ── 任务1(保留票号/审核状态/已填字段)
        [框: B] ── 任务2(新建)
```

**交互建议**:操作员**只画 B 的框**,系统检测到它和任务 1 的框重叠 →
**自动把任务 1 的框收缩到不含 B**,并把结果显示出来让人确认。
一个动作完成,**中间那个"原框还罩着两张"的坏状态从不落库**。

---

## 三、真正的坑:字段跟错了票(这才是会静默出事的地方)

拆框解决了"裁哪块",但还有一层:

> 任务 1 原来的字段,是从**罩住两张票的大框**里读出来的。
> 它读到的票号**可能是 B 的**。拆框后任务 1 拿着 A 的框、B 的票号 ——
> **交付时「票号B.jpg」里装的是 A 的图。**

这个错**不会报错、不会拦截**,上家收到的是一个票号对不上图的文件。
**这是整个方案里最危险的一处**,比切图本身危险,因为切图错了看得见,这个看不见。

### 解法:拆完不要人工猜,让机器重读

`lib/qwen_ocr/qwen_split_service.js` 里的 **`retrySuspectReceipt` 已经能做这件事**
(2026-07-06 的漏切保险):

- 按框裁出子区域(带 4% padding)
- 单独重喂一次 qwen
- **把子结果的 bbox 映射回全图坐标** ← 最难写的一段,已经在生产跑

拆框后对**两个新框各跑一次**,字段各自重读 → **框和字段天然对齐,不需要人去对应。**

### 顺带白捡一个检测

> 重读出来的票号 **≠** 任务 1 原来的票号
> → 说明原字段本来就是隔壁那张的
> → **标出来让人确认**

这正好把"字段跟错票"从一个看不见的错,变成一个会亮的提示。

### 重读失败怎么办

qwen 读不出来就人工填。但**填字段时界面必须显示"框内那一块"的预览,而不是整张原图** ——
让人对着 A 的画面填 A 的票号。否则人也会看错票。

---

## 四、交付时的完整链条(三层锚定,每层都不靠猜)

```
① 框  → 决定裁哪一块          (人画的 / 模型给的,机器执行)
② 票号 → 决定文件叫什么名      (从框内重读出来的,不是人凭印象填的)
③ 护栏 → 裁片完整包含兄弟框?  (是 → 拦下,写进「导出说明.txt」)
```

再加拆框时的那条:**重读票号 ≠ 原票号 → 提示确认**。

四道加起来,"新加的是哪个小票"在**每一层都有确定答案**,没有一处需要推断。

---

## 五、对分期的影响

**第 2 期的定义要改**:不是"手动加一张小票",而是 **"拆框 / 画框 / 改框"**,
并且**必须带上拆完重读字段**。理由就是第三节 —— 只做拆框不重读,
会把一个看得见的切图问题,换成一个看不见的票号错配问题,**那是变坏不是变好**。

| 期 | 内容(修订) |
|---|---|
| 1 | 审核台整图 + 框显示 |
| **2** | **拆框 / 画框 / 改框 + 拆完自动重读字段 + 票号变化提示** |
| 3 | 交付时按框裁(中线外扩)+ 完整包含护栏 |
| 4 | 识别侧 `split:'boxes'` |

第 2 期比原估的大一点(多了重读接线),但**重读的核心零件是现成的**,
主要是把 `retrySuspectReceipt` 从"识别期自动触发"改成"也能被审核期手动调用"。
