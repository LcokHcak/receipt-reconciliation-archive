# 识别提升三批:不翻倍配置(2026-07-21)

用户拍板:不接受 API 调用翻倍(二批 always 全店双读 +91% 被否)。本批实测三条替代路,
选型仍用 80 张生产代表性随机样本(stage2)+ 生产原值投影口径(同二批)。

## 一、三条路实测结论

1. **条码本地解码(采纳,零 API)**:新罗/现代票号印顶部 Code39、乐天/济州印票底,
   zxing-wasm 本地解码。实测存量切片(压缩上限 2400px)解码命中 ~26%,**命中零误码**
   (不匹配的全是营销 QR,已按一维码格式过滤)。生产 23 张错票号里白救 4 张,
   并给串尾个位混淆(锚点+双读都难保的形态)提供唯一零成本解。
   注:客户库近月工作区已被库清理删除、批次切片即最高清存量——26% 就是存量真实水平;
   若未来在**上传入库时**(压缩前的原相机图)解码,命中率可期 60%+(立案 P6,本批不动)。
2. **二遍换便宜模型(淘汰,数据说话)**:生产 23 张错票号,二遍读对数
   qwen-vl-max=11 / qwen-vl-plus=7(还慢 5 倍) / qwen-vl-ocr=更差(常回空串丢修复)。
   二遍是裁片小图、token 本来就少,省的钱补不回丢的修复量。QWEN_REPAIR_MODEL 保留为
   env 旋钮,默认跟主模型。
3. **按店分档双读(采纳)**:新增 QWEN_RECEIPT_NO_REPAIR_ALWAYS_STORES——
   anchor 全局档下仍强制双读的店,默认 SHINSEGAE,HYUNDAI(错误率最高、体量最小 20.7%)。

## 二、配置菜单(投影=生产原值 77.5% 为底 + 该配置对生产错例的实测翻正/条码救回)

| 档 | 配置 | 投影 | 调用增量 |
|---|---|---|---|
| A | 全店 anchor 触发二遍 + 条码 | 88.2% | ~+25% |
| **D(新默认)** | **新世界/现代 always 双读 + 其余 anchor + 条码全员白检** | **89.8%** | **~+35%(不翻倍)** |
| E | 全店 always 双读 + 条码 | 91.1% | +91%(要冲顶 env 升 `QWEN_RECEIPT_NO_REPAIR_MODE=always`) |

条码白检层对所有启用店每张执行(纯 CPU ~0.3-0.6s/张,仅弱值或双读需要时才可能追加 API):
解码载荷须整体通过店锚点规格才采信;与 AI 读数一致=免费互证跳过二遍;
不一致=采条码值+`receipt_no_barcode_adopted` 红标;多候选歧义(同框多票)放弃不猜。

## 三、改动清单

- 新模块 lib/qwen_ocr/receipt_no_barcode.js(zxing-wasm 惰性加载;解码是白捡不是闸门,
  任何失败静默回退)+ 依赖 zxing-wasm@^3(纯 WASM 无原生编译,2c4g 服务器可跑)
- adapter:条码层前置于二遍;QWEN_RECEIPT_NO_REPAIR_ALWAYS_STORES(默认 SN,HY)
  + QWEN_REPAIR_MODEL(默认主模型);全局默认档回 anchor
- 前端 reviewReasons:receipt_no_barcode_adopted 文案+字段高亮
- 测试:写码→解码回环 / 候选筛选(锚点闸+歧义放弃) / 适配器零 API 采纳 / 无码回退二遍

## 四、诚实边界

- 89.8% vs 90 目标差 0.2pp,在 n=80 的 ±5pp 噪声带内——部署后跑错误矩阵(全量金标)
  才是终审;若实测差口,升 E 档一行 env 的事。
- 条码 26% 命中是存量图天花板;P6(上传时解码)是把它抬到 60%+ 的正路。
- 双读/条码都救不了"图糊到人都读不出"——那部分靠红标+重拍流程,本来也不该算 OCR 的账。
