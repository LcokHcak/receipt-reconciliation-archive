# 配置台架构设计(方案 v1,待拍板)

> 2026-07-14。对应你给的配置台方案(模式勾选审核字段+导出配置+冲突检查+一键保存+修改日志)。
> 本文回答三件事:**为什么这么做是对的**、**它在现在的系统里怎么落**、**会撞到哪些边界、怎么防**。

---

## 一、为什么要做配置台(业务视角)

### 1. 变更频率与发布成本的错配

过去 6 周实际发生的规则变更:百货三家接入、现代票号 16→8 位纠正、乐天门店 4 码、
品牌白名单 3 个、新世界上家固定梁总、两个新模式收编(新罗V团-本司/新世界PKG-宋总)、
S 活动动作签、百货免护照口径两轮细化——**每一条都是代码+测试+部署**。
这些变化里 90% 是"业务词汇内的重组"(哪些字段、怎么分类、怎么命名、记不记),
不是新能力。配置台把这 90% 交给业务自己,剩 10%(新字段/新校验/新识别)留给代码。

### 2. 审核↔导出失步是有前科的事故模式

- cb24667 结算 Internal error:小票号规则四份副本失步;
- 复核 HIGH#1(昨天):免护照放行没对齐乐天交付包的护照图要求,差点交付日整批爆雷;
- 审计 #4:模式矩阵只作用于台账导出,结算/交付各走各的。

配置台的**冲突检查**(导出要的字段,审核台必须产得出)把这类"交付日爆雷"前移到"配置时提醒"。
这是配置台最大的架构价值,比"省一次部署"值钱。

### 3. 员工可控与透明

审核员看得见"这个模式要什么",新人不用背 29 行矩阵;你自己改需求不用等工程链路。

## 三、架构设计

### 1. 总原则:配置=数据,校验=代码,出厂=兜底

```
┌─ 配置台 UI(admin)──┐      ┌── 消费方(全部只认 resolver)──────────┐
│ 模式配置/店家档案/   │ 写   │ 审核台必填集  getRequiredFieldRules   │
│ 导出计划/冲突检查    ├────→ │ 台账导出列    ledger bridge          │
└─────────────────────┘      │ 交付包结构    delivery exports        │
        ↓ 版本化落库          │ 前端面板      reviewFieldConfig       │
┌─ config 存储(SQLite)─┐     └──────────────────────────────────────┘
│ 每次保存=新版本,      │             ↑
│ active 指针,永不覆盖  │      ┌──────┴───────┐
└──────────────────────┘      │ resolver:     │
        ↑ seed                │ DB配置 → 命中用它│
┌─ 出厂配置(现有代码)──┐      │ 没配/坏 → 出厂  │
│ mode_record_matrix    ├────→│ (系统永不因     │
│ store_profiles        │      │  配置挂掉)      │
└──────────────────────┘      └───────────────┘
```

- **出厂配置=现有硬编码**,用脚本把 29 模式+3 档案 seed 成 v1(不手抄,快照测试锁"seed≡矩阵")。
- 配置解析失败/字段不认识 → 整条回落出厂,报警不崩。
- **版本化是硬要求**:结算不可逆,台账行/结算记录要盖 `configVersion` 戳——
  "这批当时按哪版规则结的"必须永远答得上;修改日志=版本历史本身(免费得到,还能 diff/回滚)。

### 2. 两个实体,别揉成一个

你的 A/B/C 类勾选里藏着两种东西:

- **店家档案**(百货 C 类的字段/交易编号格式/门店码/品牌白名单/借位)——跟着**店**走,
  乐天百货的门店码规则不该复制进每个用到它的模式;
- **模式配置**(记哪些列/怎么导出/动作签/SLIM 放宽)——跟着**团号表模式串**走。

配置台做两个页签:「店家档案」和「模式配置」,模式配置引用店家档案,
而不是把百货字段抄进每个模式。否则改一次品牌白名单要点 N 个模式。

### 3. 你方案各块的落点

| 你的方案 | 系统落点 |
|---|---|
| 顶端已配置模式+新增/修改/删除 | 模式配置列表;**删除=停用**(软删,历史版本永存) |
| 模式名称录入 | 必须 normalize 后对齐**团号表模式串**(有 251 行小写 pkg 的前科);配置台显示"该模式近 30 天出现次数",没配置的模式串亮出来 |
| B类(非百货)审核勾选 | 免税店小票必填集微调(基线=现 5 字段) |
| C类(百货)审核勾选 | 从店家档案派生,模式级只微调 |
| A类文件夹导出:一级/二级/三级分类+命名 | 路径模板 DSL:`{一级}/{二级}/{命名}`,每段=单字段或多字段拼接。现有四规则全部可表达(济州道辉=`{团号}/{团号}—{姓名}{护照前4}`;S活动双份=同模式挂两个导出计划) |
| B类 Excel 导出:勾列 | mode_record_matrix columns 的可视化;**要补两样:列顺序+表头文案**(上家看的),以及**借位映射**(新世界金额→团号列是"源字段→目标列",不是简单勾选) |
| 冲突检查 | 见四.g,要分硬冲突/软警告两级 |
| 一键保存+修改日志 | 保存=新版本;日志=版本流水(操作人/时间/diff) |

## 四、边界问题(会撞的墙,提前设计)

### a. ⭐时序墙:审核在前,模式在后(最重要的一堵)

审核字段集**不能完全按模式配**:一张票进审核台时,团号可能 not_found/表还在解析/待归类——
**模式还不存在,按哪个模式的必填集审?**

设计结论:
- 审核必填集的**主键是 docType+店家档案**(现状,保留为基线);
- 模式级配置只做**增量微调**(放宽某字段/加动作签),且只在预匹配 `matched` 后套用;
- 没匹配上=基线全集。SLIM 车道就是这个形态的现成先例(三条件缺一不可)。

这样"审核台永远有确定的必填集",配置台的模式级勾选是"锦上添花层"而非"唯一来源"。

### b. 配置变更对在途批次的影响

半审批次遇到配置修改怎么办?定版本语义:
- **审核台**:实时取 active 版本(改完立刻生效,与现在改店切必填集同体验);
- **结算/导出**:动作发生时快照当时 active 版本并盖戳,一次导出一个版本,绝不半新半旧;
- **已结算行**:永不回溯。

### c. 删除/停用

模式还有在途批次/近 30 天有结算 → 只许停用不许删;停用后新票走默认全记,存量不动。

### d. ⭐「新增字段(手填)」是最大的坑

两种"新字段"必须分开:
1. **引用已注册字段**(FIELD_CONTRACT 字段注册表里有,只是没列在快捷勾选里)→ 配置台允许,下拉选,安全;
2. **真正的新字段**(OCR 不认识/存储白名单没有/normalizer 不认)→ **配置台做不到**。
   勾了也只是永远空列。这必须走代码(注册字段+适配器+白名单+迁移)。

配置台的"新增字段"按钮=①;对②给一个"字段需求登记"入口(记下来找工程),
界面上写清楚,否则配置台会给你"什么都能配"的幻觉。

### e. 文件夹命名的文件系统边界

字段值当文件夹名会撞:空值、非法字符(`/:*?"<>|`)、超长路径、重名。
- sanitize 统一走现有 `sanitizeFolderLabel`;
- **空值策略做成配置项**(每个导出计划选一个):阻断并带来源前缀(S活动缺票号的现成先例)/跳过并留痕/占位"未知";
- 重名自动 `_2` 后缀(归档改名的现成先例);
- **路径长度冲突检查**:三级分类+中文长名,Windows 下载解压 260 字符会炸——冲突检查算最坏路径长度。

### f. 生效与并发

- 30 人在线,配置读高频(每次算任务状态都要)→ resolver 内存缓存+版本号失效(与 deptRuleSetCache 同款);
- 配置写=admin 单人场景,乐观锁(保存时 version 不对=有人先改了,刷新重看)就够,不过度设计;
- 导出进行中恒用开始时快照的版本。

### g. 冲突检查要分两级,并且要"查得比字段深"

- **硬冲突(阻断启用,可存草稿)**:导出勾的字段在该模式的审核集+自动字段里**没有任何来源**
  (例:非百货模式勾"交易金额"——这字段只有百货有,永远空);
- **软警告(可启用)**:字段是选填可能为空(百货身份两件套)、路径长度逼近上限、
  模式串在团号表近 30 天零出现(可能拼错名)。
- 你截图里"导出缺少审核字段→请在审核台勾选"就是硬冲突的正确形态。

### h. 爆炸半径控制(配置台自己不能变成新事故源)

非工程师改生产行为,防线四件套:
1. 出厂兜底(坏配置→回落内置,报警不崩);
2. 冲突检查(上面);
3. **dry-run 预览**——强烈建议加:选一个最近已结算批次,试跑导出计划,
   界面直接显示会产出的文件夹树/Excel 列(不落盘)。这比任何静态检查都直观,
   员工"配完点预览"就知道对不对;
4. 一键回滚到任意历史版本。

### i. 测试策略跟着变

现有 1399 测试很多断言写死行为。config 化后:
- **引擎测试**:给定配置→断言行为(参数化);
- **出厂快照测试**:seed 出来的 v1 ≡ 现 mode_record_matrix/store_profiles(防 seed 漂移);
- **配置 schema 校验**:加载时严格校验形状,坏形状=回落+报警。

## 五、冻结区(永不进配置台)

这些是安全闸/数据完整性,配置错一次就是事故,保持代码管辖:

- 组级护照口径(passportFree 旗标在店家档案里可见,但**只读展示**);
- 批次写锁/客户锁/锁序;
- 存储格式铁律(存储永远 canonical 保杠,**配置台只能配导出形态**,不能配存储);
- 日期预检、票号 canonical 化、normalizer 白名单;
- 团号表导入/预匹配机制本身。
