# 团号确认站模块设计(实施版,2026-07-09)

> 范围:从"收票员手动把图导入系统"开始设计;微信群建模与自动收票属将来 intake 项目,本版不涉及。
> 上位蓝图:docs/团号前置工作流蓝图.md(含完整风险分析/评审过程/人时账推导)。
> 数据地基:生产 07-06~09 实测(探针 tmp/probe_flow_stats.js / probe_sameday_prior.js):
> 2834组/天;组级预匹配命中54%;小票40%没读出团号串;≥2票命中组30%组内不一致;
> 一个收票员一天的组落在30-50个团号上(top几个占大头);整组无小票仅0.2%。

## 总览:六模块

```
M0 建档导入(现有,微调) → M1 机器候选层(新,零人力) → M2 团号+模式确认站(新,人工闸)
→ M3 回执与回发(新,轻量) → M4 分车道审核(改造现有) → 结算/背书/台账/对账(不动)
                                  ↑ M5 撤销与安全绳(新)
```

## M6 在线团号表(全局当前版)——自动日批与候选统一的前提

- 存储:不动表结构,约定批次号 `__global_current__`;后勤一人一天导一次。
- 查询回退:findByTour 两级——批次自有表优先(老批次零迁移),无则回退全局当前版;新批次不再导表。
- 原子换版:先写暂存版→行数校验→一把切指针,杜绝导一半被查到。
- 防乱替代方案:预匹配/结算盖"表版本戳"(审计可查这单按哪版匹配);导入新版→自动循环所有活跃批次
  sweepBatch 重匹配(单批次 sweep 现成)。
- 收益:20人×每天(建批+传8.8MB表+等导入)的仪式 → 后勤1人1次;忘导表的 pending_table 黑洞消失
  (实测3天126张票挂在 pending_table)。

## M1 机器候选层(新,纯后端)

**职责**:识别完成后自动把"确认菜单"备好,人到站即选。

### ① 组级候选聚合器
- 端点:`GET /api/batches/:batchId/source-groups/:groupKey/tour-candidates`
- 输出:候选列表,每项 = { tourNo, 支持票数, 命中表?, 表内mode, mode内嵌代理与建档代理一致?, 来源(matched/fuzzy/groupNoSuggestion) } + 冲突清单(matched但值互异的票)。
- 纯读计算,无落盘。

### ② 收票员当日先验
- 新表 `tour_confirm_log`(SQLite):{ workspaceKey, date, tourNo, mode, confirmedBy, confirmedAt, batchId, groupKey }。
- 每次人工确认写一行;查询 `GET /api/tour-prior?workspace=&date=` 返回"该收票员当日已确认团号"按引用组数排序。
- 双重身份:先验候选源 + 确认审计流水 + 更正传播(needs_recheck)依据。
- 扩展位:预留 nullable `chatGroup` 列,将来 intake 接群后先验粒度从"人-日"升级"群-日"(实测推算每群每天仅2-3个团号)。

## M2 团号+模式确认站(核心新模块)

**位置**:审核台新 tab「团号确认」(与实时队列/代理视图并列),批次打开默认落点。

**确认卡三状态**(每屏一组):
| 状态 | 占比(实测推算) | 交互 | 目标耗时 |
|---|---|---|---|
| 多数票命中(≥2票一致) | ~14% | 绿色候选+票数+代理比对,Enter 确认 | 6s |
| 单票命中 | ~33% | 黄色候选,**强制原图团号区并排人眼比对**(误中唯一裸露面) | 12s |
| 没读出团号 | ~46% | 先验chips(数字键)→组内他票→手填即时查表 | ≤25s |
| 组内冲突(多票组的30%) | ~6% | **强制展开**:每候选值+票数+原图缩略;选主团号后少数派逐票三选一(采用/真第二团/送补救) | 20-40s |

**到站时机(事件驱动)**:组在"识别+预匹配完成"那一刻自动进确认站队列(传图后约1-2分钟/客户),
识别中的组显示"识别中"不可确认。队列随上传实时生长,与实时队列同机制。

**两种工作节奏(2026-07-09 补充,回应"一条一条 vs 攒一块")**:
- **卡片流**(一条一条):来一组处理一组,J/K/Enter 全键盘,绿组6秒,确认完立刻出回执。
- **聚合视图**(攒一块):积压组**按候选团号分簇**——同簇全是多数票绿组时可整簇一次确认
  (实测3-4组/团号,攒得越多簇越大越划算);**单票命中簇禁止批量**,逐个进卡片比对原图(防误中);
  空号组逐个先验快选。积压场景效率反而高于流式。
- **确认权限 = 收票员(自己工作区)+ 审核员(全部)**:收票员刚传完上下文最热,顺手10秒确认自己的组;
  审核员兜底扫尾。角色 fieldReview 口径。

**关键规则**:
- 手填命中团号表才亮绿允许确认为 matched;不命中 → 存「表外待核」(pending_table),换表 sweep 自动复核。
- 误中四防线:组内多数票 / 当日先验集 / mode内嵌代理 vs 建档代理 / 人工原图终审(单票必走)。
- 三信号互相矛盾 → 卡片红色不许确认,只能 deferred 送补救。
- 豁免自动盖章:百货(模式=档案常量)/ 机场票(团号"无")/ 整组无小票 → exempt,不进队列。
- 键盘流:J/K换组、数字选候选、Enter确认——5人目标的生死线。

**切图完整性(2026-07-09 补充,回应"两张小票没切开怎么办")**:
- 确认卡头部明写张数账:"N张图 → 识别出M张小票+K本护照" + 原图缩略网格——漏切靠人眼在此发现
  (机器不知道自己漏了;bbox长宽比类漏切已有"漏切二次调用"自动兜)。
- 卡上内嵌三个现成补救入口:「按此店重切」(resplit,一图多票漏切正解)/「同图补小票」(manual-receipt,
  不重识别直接补任务)/「追加图片/重拍」。点完组回"识别中",完成自动回确认站队列。
- **回执=张数核对回环**:回执文案带"收到N张小票",收票员粘回群,代理发现张数不符当场纠正——当天闭环。
- 切片切掉团号区不影响候选:字段从整图抽取,切片仅显示;对照区放原图非切片。

**落盘**(全部 additive):
- `sourceGroups[].tourConfirm = { tourNo, mode, status(unconfirmed/confirmed/exempt/deferred/mixed/pending_table), source(majority/single_matched/prior/fuzzy/manual), basis{candidates,votes,priorHit,agentCheck}, confirmedBy, confirmedAt, respondedAt, revisions[] }`
  → 必进 `createSourceGroup` 白名单(lib/source_group_utils.js,铁律)+ 新 stampGroupTourConfirm(照 stampGroupSettlement 先例)+ round-trip 单测。

**端点**:
- `POST .../confirm-tour`(照 confirmGroupModes 模板,角色 fieldReview=admin+reviewer):
  withBatchWrite → 校验表内命中 → 盖章 → 回填组内空票 groupNoFinal(**只写空票/未人工改过票;matched异值票绝不覆盖,标例外**)→ 逐票 prematchTask 重跑翻绿 → saveBatchAsync → 写 tour_confirm_log → 按模式入回发队列。
- `POST .../unconfirm-tour`(见 M5)。

**闸(两档,渐进)**:
- 软闸(P1):未确认组灰徽章提示,不拦操作,埋点收集耗时分布。
- 硬闸(P2,软闸观察≥1周且均值≤15s后开):approveSourceGroupTasks 加第四道闸(未确认→409),**ENV 开关秒回退;只拦通过/结算,不拦浏览编辑**;表外待核组允许先审后确认,防堵死。
- precheck 新 reason:`tour_unconfirmed` / `mode_action_pending`(S活动红标签未处理)。

## M3 回执与回发(轻量,无群字段)

**回执卡片**:确认成功即弹——"客户X,收到N张票,团号NNNNN(模式),异常:缺护照/第3张需重拍"。
一键复制 → 收票员自己粘回对应微信群 → 点【已回执】落 respondedAt。
**时序核心:挂确认完成,不等字段审核**——代理等待小时级→分钟级;异常清单当场带出,省隔天追图往返。

**回发队列**:确认模式 ∈ {发12/17/18号, S活动} → 自动入本收票员回发清单
(独立 repo 落盘 sendback_queue:{batchId, taskId, action, status, sentBy, sentAt, dueAt});
回发工作台:图+目标+已发盖章+超时红签+漏发看板。人肉发,系统记账。不做微信集成。

## M4 分车道审核(改造现有审核台)

车道判定唯一真相源 = tourConfirm.mode → lookupModeRecordRule:
| 车道 | 审核深度 |
|---|---|
| 不用记类(~18%) | 小票免逐字段只勾"属该团号";**护照/姓名/日期仍人审** |
| S活动 | 全字段不省 + 结算背书强制勾"红标签已处理" |
| 发群类 | 标准锚字段 + 回发队列 |
| 标准(~65%) | 锚字段(护照/姓名/日期/店);票号不逐张核对(B1拍板,对账回填);团号已锁定免查表免纠错 |
| 豁免 | 百货/机场现有流程不变 |

**Fail-safe 铁律**:未知模式/未确认/被撤销 → DEFAULT_RULE 全审;免审资格=命中表+人工确认叠加,无任何"信OCR"放行;出口过滤抹列照旧(双保险)。
**实现挂点**:后端 getRequiredFieldRules(workbench_task_flow.js,百货DEPT先例)加 mode 分支;前端 reviewFieldConfig 加 mode 参数——**双副本成对改+grep全库副本**(结算事故铁律)。
**灰度**:先只放「新世界SG-振华 不用记」一个模式(样本大),对账两周无回归再扩。

## 人时账

现状 ~90s/组×2834组/天≈8.9人(还不含查团号/纠错/回溯沟通)。
改后:确认~15s + 回执4s + 审核~50s ≈ **70s/组 → 10人余量充足,7人可运转**;
5人=数据触发(确认站≤10s/先验命中≥70%/免审兑现≥18%/异常率≤5%),配熔断(积压>1天回撤)。
