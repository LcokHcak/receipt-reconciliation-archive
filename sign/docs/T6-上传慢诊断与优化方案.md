# T6 · 上传慢诊断与优化方案(2026-07-21,全实测)

## 一、实测数据(生产日志 + 现场测量,非推断)

| 测量项 | 结果 |
|---|---|
| 今日真实上传(110 次,陈强等操作员) | **avg 22.9s · p50 4.4s · p90 93s · max 184s** |
| 今日识别 preprocess(112 次/客户) | avg 11.6s · p90 22s · max 108s(**异步后台,不堵操作员**) |
| 本机→服务器实测吞吐(与操作员同办公室网络) | **78-133 Kbps**(234KB 分块传输 24s) |
| 历史印证 | 8.8MB 团号表上传 89s ≈ 810Kbps(2026-07 复诊记录,波动区间一致) |
| 今日上传图片实际大小(140 张) | **均值 329KB**(微信转发图,已被微信压过) |
| 压缩空间实验(真实照片 4 张,2400px/q82 重压) | **1.0×,反而略增大**——微信图已压到位,前端压缩无收益 |

**闭环验证**:3 张图/客户 ≈ 1MB ÷ ~100Kbps ≈ 90s = 实测 p90 93s,严丝合缝。

## 二、根因结论

**上传慢的唯一根因 = 办公室(韩国)→ 腾讯云广州的跨境单 TCP 上行,实际仅 ~0.1-0.8 Mbps 且波动**。
服务端处理(HEIC 转码/压缩/归档)与图片大小都不是问题——图已经很小,管道本身就是全部瓶颈。
识别(qwen)p90 22s 且为后台异步,不是操作员卡顿主因;识别线换 qwen3-vl-plus 后吞吐慢 2-3×,TPM 重测归识别专项另案。

## 三、优化方案分层(按杠杆排序)

### A|治本(基础设施,零代码,需拍板)
**腾讯云全球加速 GA / 动态加速入口**:在首尔/香港设接入点,操作员上传走就近节点→腾讯内网回源广州。
- 预期:跨境单 TCP 的丢包重传消失,吞吐 10× 以上(p90 93s → <10s);
- 成本:GA 按带宽计费(小带宽档每月几十到几百元级),**零代码零迁移**;
- 备选:整机迁香港/首尔节点——治本但迁移成本高(17.6 万硬链 rsync 经验在册),不建议先做。

### B|治等待(前端改造,拍板后我做,预计 1-2 天)
**上传后台队列**:点「建档」即入队并立刻清空表单可录下一个客户;队列按序单连接稳传+失败重试+每客户进度签(成功✓/失败重试按钮)。
- 本质:操作员录入吞吐与管道速度**解耦**——管道再慢,人不用等;
- 保序红线不破:仍是串行按序上传(串图事故前科,不做多客户并行写);
- 与 A 叠加后体验最佳;A 未上前 B 单独上也立刻止血。

### C|兜底(顺手,随 B 一起)
**>1.5MB 大图客户端压缩**(iPhone 直传原图场景 10× 收益;微信小图自动跳过,不做无用功)。HEIC 浏览器解不了,原样透传走服务端既有转码。

### D|不建议
多 TCP 并行分片上传:跨境丢包下确实有效,但破保序红线且 A 方案上了就不需要;PREPROCESS 并发已 10、识别不必陪跑此项。
