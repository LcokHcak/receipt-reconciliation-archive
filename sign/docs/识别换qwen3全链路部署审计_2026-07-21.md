## 三、换 API 会出什么问题?—— 排查清单(严重度排序)

### 已修(本次 commit)
- ⭐**BLOCKER(我上一个修复引入的回归):** sidecar 加模型闸后,无证件/兜底 sidecar(`qwen_no_document`)
  没打模型戳 → 换模型后每张无证件图(约 5%)每轮识别都重调 qwen,永不进缓存。
  **已修:** `qwenFallbackAnalysis`(batch_processing_service.js)+ split 0 文档兜底(qwen_split_service.js)
  都补齐 promptVersion+ocrModel+ocrMaxEdge 戳,首次识别后进缓存。

### ⭐历史图不重跑(用户要求"从以后的开始")——代码天然满足,已核实
- **已建档/已交付的历史任务不会被换模型自动重跑。** 重识别是显式操作(`POST /api/batches/:batchId/tasks/requeue`,
  必须传 taskIds,handler 注释"为防误操作不支持整批隐式重跑"),没有任何自动扫历史重识别的路径。
  `ensureQwenSidecar` 只在**建档(classify/build)**时被调,已建档批次不会重读 sidecar。
- **换模型只影响:** ①新上传的图(全新 qwen3+高清预处理)②在途未建档的图(预处理过但还没建成任务,数量有限)。
  所谓"重预处理浪潮"只是这批**在途 backlog**,不是全部历史——历史交付不受影响。
- **动作:** 直接翻 env 即可,新图从此走 qwen3;**不要手动 requeue 历史任务、不要跑历史重识别扫描**(那才会花钱重跑旧图)。
- ⭐**并发不用降(压测纠正,2026-07-21):** 原以为高清要把 `PREPROCESS_MAX_CONCURRENT` 降到 3-4——那是拿 qwen-vl-max
  老限额外推,**压测证伪**:qwen3-vl-plus 并发打到 64 / TPM 100 万都 0 个 429(见 docs/qwen3压力测试报告)。
  现值(生产 10)保持即可,甚至可上调缩短大批量耗时。仍建议部署前去阿里云看一眼**日配额/余额**(分钟级速率没问题,日总量另算)。
- **HIGH 无模型回退:** model 从 env 读一次、无 fallback。qwen3 若 403/宕机 → `concurrency_pool` 判 403 非可重试直接抛
  → 全链路 OCR 静默退人工、无告警。**动作:** 部署前用生产同一 `qwen_client` 路径对 qwen3-vl-plus 打一张真图确认
  200+JSON;建议加 `QWEN_FALLBACK_MODEL`,403/model-unavailable 时回退 qwen-vl-max 重试一次。
- **HIGH 护照 MRZ:** 已实测 qwen3@2048 护照号 **97%(与 max 97% 持平,无回归)**;`resolvePassportNo` 纯数学模型无关。
  注:`mrz_parser` 有 checksum 碰巧过就自动放绿的假阳性通道(历史 6CHN02041),换模型不改变该逻辑,维持监控即可。

### 部署首周盯
- **MEDIUM 零埋点:** `getUsage()`(调用量/token/失败率)生产从不被调用。换模型+高清同时改变量价失败率却不可见。
  **动作:** 按批把 getUsage 快照打日志(calls/token/errors/model)+ 统计每批 qwen_failed;盯 token/日调用/失败率三曲线设阈值告警。
- **MEDIUM TPM/退避:** qwen3-vl-plus 的 RPM/TPM 与 max 不同(需阿里云控制台核),`withRetry` 仅 3 次短退避,
  持续限流会把可重试的 429 拖成 qwen_failed 退人工。**动作:** 核额度定并发;把 maxAttempts/baseDelay 提高(如 5 次/2s)。
- **MEDIUM 超时:** `timeoutMs=90000` 硬编码未从 env 透传;高清超时触发最坏 3×90s 重传放大尾延迟。**动作:** 透传 `QWEN_TIMEOUT_MS`。
- **LOW response_format:** 请求恒带 `response_format:json_object`;157 张 q3 回放 JSON 正常,基本可信;
  仍建议启动自检,不被接受时降级为无 response_format + parseJsonLoose 兜底。
- **LOW 二遍/补救分辨率未纳入 sidecar 戳:** 调 `QWEN_REPAIR_MODEL`/`QWEN_DEPT_RESCUE_MAX_EDGE` 不作废存量缓存(advisory,二遍不夺权影响小)。
- **INFO 硬链 sidecar 安全:** customer_batch_bridge 用 copyFile 非 link,重预处理改写不穿透客户库副本。
- **INFO 条码互证层模型无关:** 5 店 zxing-wasm 纯本地,是换模型下的稳定器。

## 四、速度怎么更快?—— 按性价比

| 手段 | 预期 | 工作量 | 要点 |
|---|---|---|---|
| ⭐**上下文缓存(系统 prompt 稳定前缀)** | 输入成本 −20~30%、pass1 延迟略降 | 极低 | system prompt 一天内字节稳定、在 messages[0],正好可缓存;现请求无缓存指令、也没读 `usage.prompt_tokens_details.cached_tokens`。先打点看命中率,按官方开关开启 |
| ⭐**pass1 与二遍解耦:pass1 降 1600/1280** | 单图 token −56~72%、总成本 −35% | 中(加 env) | pass1 顶 2400 主要为整图直读票号,但票号权威已是高清裁片二遍;bbox/类型/店/日期对分辨率不敏感。⚠️**护照号 98% 全靠 pass1 的 MRZ、无护照高清二遍**——pass1 降分辨率会伤护照(占一半图)。方案:护照走高清 pass1、小票走低清 pass1+高清票号裁片二遍(按类型分档) |
| **Batch API** | 输入输出 5 折 + 提吞吐 | 中 | 预处理非实时,可走阿里云 Batch(异步)省钱提吞吐;代价=延迟(异步)、要改调用编排 |
| **anchor 模式(非 always)+ 条码优先** | 省二遍调用 | 低(env) | 弱值才二遍;条码命中直接跳过 API 二遍 |
| **并发按 qwen3 TPM 重标** | 防排队 | 低 | 核 qwen3 TPM 后设 `PREPROCESS_MAX_CONCURRENT` |

**最优组合:** 上下文缓存 + 按类型分档分辨率(护照高清 pass1 / 小票低清 pass1 + 高清票号二遍)+ anchor 模式 + Batch(可选)。
这套能把 qwen3@2400 的延迟和成本再压一截,同时保住护照 98% 与票号 90%。

## 五、部署 runbook(最新最精确方案)

1. **改代码(已完成本次):** sidecar 模型/分辨率戳 + 兜底补戳。
2. **核 qwen3-vl-plus:** 阿里云控制台确认权限/RPM/TPM/图像 token 计费;生产 qwen_client 路径打一张真图冒烟(200+JSON)。

4. **灰度翻 env:** 先一个小 workspace 设 `QWEN_OCR_MODEL=qwen3-vl-plus` + `QWEN_MAX_EDGE=2400`(高清期 `PREPROCESS_MAX_CONCURRENT=3~4`),
   观察准确率(跑错误矩阵)、429 曲线、失败率;稳了再全量。
5. **部署后终审:** 跑全量错误矩阵(零成本金标)复核真实生产准确率——切片实测 89.8% 是下界,生产整图应更高。
6. **下一步立项:** P6 上传时原图识别/解码(破新世界、全局稳超 90 的正路)。
