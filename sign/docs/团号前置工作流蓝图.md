## 1. 新工作流站点图(文字版)

```

  微信群收图 → 建批次(前置硬性,现有) → 建档:
  【微信群】必填下拉(群主数据带出代理名,替代 agentName 自由文本+localStorage回填)
  → 落 customer.sourceChatGroup + task.sourceChatGroup/customerAgentName(白名单修复后)
  耗时:~30s/客户(仅多一次下拉)
      ↓
站1 机器预处理(系统,零人力)
  qwen切图+字段抽取(sidecar) → 预匹配三触发点照旧(识别完成/换表sweep/保存重跑)
  新增:组级候选聚合器(组内票级结果聚成候选清单,按支持票数排序)
       + 同群先验查询(该群当日已人工确认的团号集合,标注"先验命中")
  纯 advisory,不落任何自动确认。~18s/图机器时
      ↓
站2 团号+模式确认站(★新增·人工闸,fieldReview角色=admin+reviewer)
  按微信群分列的组队列,一屏一组确认卡。
  确认 → 盖 sourceGroups[].tourConfirm → 回填组内空票 groupNoFinal(触发点③重跑翻绿)
       → 按 mode 定车道 → 生成回执文案 → 时效动作入回发队列
  未确认组:硬闸只拦 approve/settle(ENV开关),不拦浏览编辑,防堵死。
  百货(模式=档案常量)/机场票(团号'无')自动盖 exempt 豁免。
  耗时目标:多票一致组≤6s / 单票matched~12s(强制原图比对) / 冲突组20-40s / 空号组~25s(冷)
      ↓
站3 回执/回发站(确认站同屏 + 独立回发工作台)
  A. 回执:确认成功即弹回执卡片(群名+代理+客户+收到N票+团号+模式+异常清单如缺护照/需重拍)

  B. 回发队列:发小票17/18群/发12号/S活动红标签,确认即入队(不等审核,

  不做微信集成(全仓零集成),人肉发+系统记账审计。~4s/组
      ↓
站4 分车道审核站(改造现有审核台)
  只放行 tourConfirm=confirmed/exempt 的组(硬闸期)。按确认mode查 lookupModeRecordRule 分四车道
  (见§3模式分流表)。团号字段已由站2锁定,审核台免查表免纠错。
  耗时:SLIM~25s / 标准~48-55s / 特殊~90s(现状90s全审)
      ↓
站5 确认即结算+模式背书(现有,零改动)
  最后一张确认→approveAndSettleGroup五步编排→权威终匹配tourMatch→弹模式面板confirmGroupModes人工背书。
  仅加 preCheckGroup 两个新reason:tour_unconfirmed / mode_action_pending(S活动无红标签回执)。
      ↓
站6 更正/撤销站(新增,分层)
  未结算:unconfirm-tour → 组退回站2;模式曾为SLIM→组内已reviewed强制清false补审(安全绳)。
  已结算:过渡期人工SOP+月度对账兜底;correct-tour编排独立立项(见§8拍板项3)。
```

## 2. 团号确认站完整交互

### 2.1 候选来源(优先级排序;全部只是候选,落盘必须人点,绝不信裸OCR)

| 优先级 | 来源 | 呈现 | 可信度处理 |
|---|---|---|---|
| ① | 组内多数票:≥2票 prematch matched 且值一致 | 绿色高置信候选,标"N票命中" | 可秒确认(仍须人点) |
| ② | 单票 matched | 黄色普通候选 | **永不给秒确认**:必须原图团号区与候选值并排、人眼比对后点确认(误中=读错撞上26272个表内团号的场景恰好长这样) |
| ③ | 同群同日先验:该 sourceChatGroup 当日(可扩±1日)已人工确认的团号 chips | "本群今日已确认×M"徽章,一键点选 | 只做候选排序,永不自动填;对40%空号票和"乐天H团-本司1万候选"是把候选空间从26k缩到个位数的关键 |
| ④ | fuzzy_candidate(现有:表内唯一编辑距离≤1) | 纠错候选,diff高亮 | 人工点击采用(=人工确认) |
| ⑤ | 手填 | 输入即时查表(findByTour+normalizeTourNo兜底) | **命中表才亮绿允许确认为matched**;不命中→只能存"表外待核"(团号表滞后场景),换表 sweepBatch 自动复核翻绿 |

**正交交叉信号**(设计2独有,保留):候选团号在团号表里的 mode 串内嵌代理名(如"乐天SG-本司")与建档群带出的代理比对,不符亮红——这是与OCR完全独立的验证维度。

### 2.2 组级确认与回填

- 确认落 `sourceGroups[].tourConfirm`(照 stampGroupSettlement 盖章模式),**组级是闸和回填器,不是台账真相源**——台账仍按票级 groupNoFinal 走结算权威终匹配,advisory/权威边界(group_code_prematch_service.js:11)不动。
- 回填规则(硬约束):只写"groupNoFinal 为空 或 ==groupNoAuto"的票;**人工改过的票、matched但值≠组级团号的票绝不覆盖**,标"组内冲突/例外"留人裁决(实测≥2票matched组30%内部不一致,不能假设一组一团号)。
- 回填后逐票 prematchTask 重跑(复用触发点③,幂等),徽章自动翻绿,零新匹配逻辑。
- 真业务一组多团号 → status='mixed' 退回逐票分派,不强行组级。

### 2.3 冲突处理(30%组内不一致)

确认卡**强制展开,不许一键**:每个候选值一行 = 值 + 持有票数 + 各票原图团号区裁剪缩略图 + 是否命中表 + 对应mode/代理比对结果。人选主团号后,少数派票逐张三选一:**采用主团号 / 保留为第二团号(真跨团) / 送补救**,裁决落 basis。三信号互相矛盾(多数票团号的mode代理与建档群代理不符等)→ 卡片红色,不许确认,只能 deferred 进补救队列——冲突强制人工是误中的最后防线。

### 2.4 没切开的团号(40%空状态)

数据没丢:字段从整图抽取,切片只是显示。确认卡直接内嵌**客户库原图**(original-image API 现成,切片名反查 _original.*),操作顺序:先点同群先验chip(热态大多秒选)→ 组内他票候选 → 手填+即时查表。原图也看不清 → 站内快捷入口转补救七件套:**resplit按店重切**(qwen重切,一图多票漏切正解)/ **manual-receipt同图补小票** / 追加图片插队 / 重拍标记。
⚠️前提:P0归因摸底必须先证实40%空状态主体是"团号没读出"而非管道故障(毒sidecar有前科)——若是管道故障,先走 purge_sidecar_requeue SOP 修管道,人时账另算。

### 2.5 识别错的团号

- **(a) 读错没撞表**(not_found/fuzzy):无资损风险,fuzzy一键采用/先验/手填,慢但安全。
- **(b) 误中**(读错撞上表内有效团号):四道叠加防线——组内多数票不一致亮红 / 不在同群先验集亮黄("该群今天没人确认过这个团号")/ mode内嵌代理与建档代理不符亮红 / 人工确认时原图团号区并排人眼终审。单票组无多数票,故**单票matched永远走原图比对**。
- **(c) store_mismatch**:展示表内候选模式提示店家错位,先纠店再确认。
- **(d) 确认后发现错**:未结算 → unconfirm-tour 撤销重确认(SLIM改ALL强制补审);已结算 → 过渡SOP+月度对账,correct-tour独立立项;先验引用链传播 needs_recheck;已发回执 → 更正通知入回发队列。

### 2.6 交互形态

键盘流是5人目标的生死线:J/K换组、数字键选候选、Enter确认。按微信群分列队列。灰度开关照 mergeSettleOnConfirm 的 localStorage 先例,默认关。

## 4. 溯源与回发设计

### 4.1 群主数据与落盘链
- 新增 chat_groups 主数据(json,量小:~400群↔~20代理↔收票员),admin维护CRUD;建档下拉强制从主数据选(允许新建条目降低阻力),代理名由群带出只读——同时根治 agentName"自由文本+localStorage回填全靠手感"的数据质量问题(先验的前置条件)。
- 字段链(照 agentName 现成十处路径):customer.sourceChatGroup(customer_record.js:57字面量,customer侧{...record}展开无抹除风险)→ 桥接注入 task.sourceChatGroup(customer_batch_bridge_service.js:200旁)→ workbench_task_factory 落字段 → **normalizeTask白名单同步加**(铁律主现场)→ sourceGroups组级挂群标签(source_group_utils.js:151铁律)。
- **命名铁律**:避开 sourceGroup(已被~50个文件占用=批次内客户组),用 sourceChatGroup。

### 4.2 回溯UI(纯前端,后端零改动)
审核台组头回溯条:**群名·代理·建档人·建档时间**——数据已被 loadReviewCustomerNames 整包拉到前端只是被丢弃(ReviewView.vue:211-240),捡回即可;点群名筛出该群当日全部组;点开原图走 task.sourceOriginalPath 直接拆解(零扫描),不走O(全库)的 findCustomerByReviewReference。

### 4.3 立刻回应代理(时序改变:回执挂"确认完成"而非"全审完")
代理在群里等的是"收到了/是这个团/要补什么"——站2确认完就能给,不等字段审核:
- **回执卡片**:群名+代理+客户+收到N票+团号+模式+**异常清单(缺护照/需重拍——省掉的补图往返是账面外真实收益)**,一键复制→人肉粘回群→respondedAt落盘;收票员看板加"待回执"列。
- **回发队列**(sendback_queue独立repo落盘,不挤batch白名单):{batchId,taskId,chatGroupName,action,status,sentBy,sentAt,dueAt},确认即入队,回发工作台按群分组+大图+已发盖章+超时红签+漏发看板——补齐现状"动作签纯展示、零回执、无法审计漏发"的洞;动作签覆盖面从被matched钉死的37%→确认组100%。
- 确认被更正→自动生成"更正通知"再入队(共同盲区补偿)。
- 明确不做微信/企微集成(全仓零集成+封号合规风险),人肉发+系统记账。
