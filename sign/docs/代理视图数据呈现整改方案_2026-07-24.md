# 代理视图 · 数据呈现整改方案(2026-07-24)

> 触发:用户反馈「感觉实际审核的比左侧显示的多」+「客户组 vs 票数 到底哪个是每页的需求」。
> 本方案先讲清**目的**,再指出**现状问题**,给出**新口径 + 字段增删 + 分页单位矩阵 + 分期落地**。
> 前置已修:①投影准实时增量刷新(ae67481,数字不再冻在数小时前)。

## 一、这个页面到底是干嘛的(先对齐目的)

代理视图 = **操作员/管理者按「代理(旅行社)」维度,盯每个代理旗下客户的收票→审核→结算进度,及时发现卡住的活。**

- **工作单位是「客户组」**:一个客户 = 一位旅客(护照 + 他的一沓小票),操作员/审核员是**一整组一整组地处理**(审一个客户的所有票、给一个客户结算)。所以"还有多少要处理"天然按**客户组**数。
- **产出单位是「票」**:每张小票 → 一条台账 → 交付给上家。业务量、交付量按**票**算。
- 结论:**代理视图主看客户组(进度/工作量),票数是辅助的"业务量"读数**——两者不是二选一,是主次分工(见第四节矩阵)。

## 二、现状为什么"看着不准"(三个真问题)

1. **投影滞后(已修)**:页面数字来自一份定期刷新的快照,审核动作本身不刷它。没重启/没跑 cron 就冻在上次刷新时刻(实测滞后 385 分钟≈6.4 小时)→ 这几小时的审核全没算进"完成"。**这是"实际比显示多"的头号原因,已加应用内增量刷新止血。**

2. **统计卡口径重叠、桶不互斥、加起来 ≠ 总数**(信任崩塌的根):
   - 现 7 卡:总数 / 待审核 / 完成 / 未完全通过 / 今日新增 / 今日审核批次 / 异常待处理。
   - `needs_remedy` **同时**进「未完全通过」**和**「异常待处理」→ 双重计数。
   - `needs_confirm` 进「未完全通过」;`tour_pending`+`review_pending` 进「待审核」。
   - 于是:`待审核 + 完成 + 未完全通过 + 异常 ≠ 总数`(有的漏、有的重),用户一加发现对不上 → 觉得"不准"。**这是最该修的。**

3. **"待审核"把两种完全不同的活揉一起**:`tour_pending`(小票待表态/匹配团号=**操作员**的活)和 `review_pending`(字段待人核=**审核员**的活)。两拨人、两种动作,合成一个数,既看不出谁的活,也无法分工。

4. **X/Y 语义不明**:卡片 `42/906` 实为 `当前代理/全部代理`,但没标注,用户不知道分子分母是什么。

5. **全是客户组、看不到票数**:一个客户 5 张票在这里只算 1(客户组),用户潜意识按票数期待 → 落差感。整页无任何票数读数。

## 三、新口径(核心:6 个**互斥**状态 → 卡片桶必和为总数)

底层 `review_status` 本就是**单客户单一最高优先级状态**(6 个,互斥):

| review_status | 建议中文 | 谁的活 | 含义 |
|---|---|---|---|
| `passed` | ✅ 已完成 | — | 审完 + 已结算入台账 |
| `review_pending` | 🕐 待审核 | 审核员 | 字段待人核 |
| `tour_pending` | 🔗 待匹配团号 | 操作员 | 有小票未表态/待配团号 |
| `needs_confirm` | 📌 待结算确认 | 审核员/操作员 | 审完但组未结算 |
| `needs_remedy` | ⚠️ 待补救 | 操作员 | 异常补救 |
| `rephoto` | 📷 需重拍 | 代理/操作员 | 图不清需重拍 |

**卡片桶必须建立在这 6 个互斥态之上,任何客户只进一个桶,所有桶之和 = 总数。** 这是"数字可信"的地基。

### 建议:从 7 张重叠卡 → 4 张互斥卡 + 1 行活动指标

**主行(状态,互斥,和为总数):**
| 卡 | = review_status | 一句话 |
|---|---|---|
| **客户组总数** | 全部 | 分母 |
| **✅ 已完成** | passed | 审完已结算,不用管了 |
| **🔄 流程中** | tour_pending + review_pending | 正常往下走,操作员/审核员日常推进 |
| **⚠️ 待人处理** | rephoto + needs_remedy + needs_confirm | **要人干预的**(重拍/补救/确认结算)——这才是"卡住待办"的真数字 |

> 已完成 + 流程中 + 待人处理 = 总数(互斥,可对账)。"待人处理"合并三种需人工介入的态,是操作员**每天真正要清的队列**,比现在拆成"未完全通过/异常"两张重叠卡清晰得多。想细分时点开卡再展开 6 态明细。

**副行(活动/量,不混进状态桶):**
| 卡 | 含义 |
|---|---|
| **今日新增** | 今天新收的客户组(活动指标) |
| **今日已审** | 今天投影刷新且进入审后态的批次/客户(活动指标) |
| **总票数(辅)** | 该视图范围内的小票总数——**给业务量一个票口径读数**,解决"看着比客户组多"的落差 |

**X/Y 明确标注**:卡片副标题写「当前代理 / 全部代理」,或分子分母加 tooltip;只选了某代理时高亮分子。

## 四、客户组 vs 票数 · 分页单位矩阵(全系统口径统一)

| 页面 | 主单位 | 辅单位 | 理由 |
|---|---|---|---|
| **代理视图** | **客户组** | 票数(总量) | 操作员按组处理进度;票数给业务量参考 |
| 审核台 | **票** | 客户组(分组) | 审核员逐票审 |
| 资料库/交付 | **票** | 客户组 | 交付单位是票 |
| 未收对账 | **票** | — | 催收按票 |
| 月度/账单 | **票** | 客户组 | 计费按票 |

一句话:**只有代理视图以"客户组"为主**(因为它是"盯人/盯进度"的管理视图),其余都以"票"为主。所以代理视图保留客户组为主 + 补一个票数辅读数即可,不必推倒。

## 五、表格字段增删(现 9 列 → 收敛)

现:序号 / 姓名 / 收票时间 / 图片数 / 审核状态 / 免税店 / 模式 / 下一步任务 / 操作

| 字段 | 处置 | 说明 |
|---|---|---|
| 序号 | 保留 | 定位 |
| 姓名 | 保留 | 客户身份 |
| 收票时间 | 保留 · 改叫「收票日」| = 上传那天(已统一口径);时刻精确到分意义不大,按日即可 |
| 图片数 | 保留 · 改叫「票/图数」| 这就是该客户组的票数,标签点明 |
| 审核状态 + 下一步任务 | **合并成一列「状态 · 下一步」** | 下一步任务是状态派生的(状态→动作一一对应),两列信息冗余;合成"状态徽章 + 动作按钮"一列 |
| 免税店 / 模式 | 保留 | 业务定位 |
| 操作 | 保留 | 去审核台 |

净效果:**9 列 → 7 列**,去掉冗余的"下一步任务"独立列,收票时间/图片数标签点明业务义。
