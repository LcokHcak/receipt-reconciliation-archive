# 资料库交付工作台设计(2026-07-16,已并入 architect 复核收口)

> 目的:把资料库从"已结算客户查询表 + 5 个写死导出按钮"升级成**交付工作台**——
> 操作员打开页面 10 秒内知道:**今天有什么可以交付、还差什么、发出去了没有**。
> 与配置台的关系:**配置归配置台(admin),执行归资料库(操作员)**,导出计划是两者之间的唯一契约。
> 本文档已按 architect 对抗性复核(2026-07-16,2C/5H/4M/2L)修订,复核结论见第八节。

---

## 一、现状诊断(代码定位)

现状 = `frontend/src/views/LibraryView.vue` + `services/monthly/library_mode_export_service.js`
+ `routes/monthly/export_routes.js`(Excel)+ `routes/workbench_routes.js:70-74`(交付包,fieldReview 守卫)。

### 1. 配置台和资料库是两个世界(最大断层)

配置台 P2 已经有完整的"导出计划"实体:builtin/DSL/Excel 三型、版本化、预览、blocked/collision 硬闸、
真落盘执行(`lib/export_plan_engine.js` / `services/export_plan_execute_service.js`)。
但执行入口在 **admin-only** 配置台(`routes/config_console_routes.js` 全套 protect);
资料库——操作员真正干活的地方——还是 5 个写死按钮。后果:

- 配置台新配的 DSL/Excel 计划,操作员用不上,得 admin 代跑;
- 计划的 scope(圈了哪些模式)、就绪状态,资料库完全不感知;
- 新上家接入 = 配置台配完计划,资料库无入口 → 配置台"放权给业务"的立项目的断在最后一公里。

### 2. 交付没有生命周期(最大业务痛点)

客户结算进资料库后,状态只有「审核完·已结算」和「需重拍」。**没有"已交付/未交付"**:

- 每天导交付包靠人记"哪个批次发过了",漏发/重发无系统防线;
- 5 按钮导出 = 同步 blob 直下,**产物不落盘、零留痕**(配置台 execute 有 audit_log,资料库按钮没有);
  浏览器一关 1-2 分钟白打包,重新来;
- 交付了哪版配置、覆盖了哪些客户,事后无法回答——对账出问题时没有锚。

### 3. 交付单位错位

业务交付 = **按渠道(上家)/按天**;系统导出 = **按操作批次**(交付包按钮全部强制单批次)。
一天 N 个批次的同渠道客户,要逐批次导出再手工合并文件夹。Excel 支持工作区级,文件夹/交付包不支持。

### 4. 就绪状态事后才知道

点导出 → 打包 1-2 分钟 → 422 才知道缺票号/缺护照/未审。引擎 `resolveExportPlan` 是**纯函数**,
dry-run 预检现成能力,但只在配置台预览里用。操作员的循环是:打包→报错→回审核台找票→再打包。

### 5. 性能(代码可见)

- 页面一次刷新 4 个请求;`summary` 和 `customers` **各自调一遍 `listRephotoGroups`**,
  每遍对所有 owned 批次逐个 `loadBatch`(整 JSON)——重拍扫描 O(批次×任务)且**每次刷新跑两遍**
  (`library_mode_export_service.js:141-193`,admin 每天几十个批次、历史累计后最重);
- xlsx 主线程 exceljs 构建(闸=4 并发,`export_routes.js:25`),大工作区上千行仍占主线程;
- zip 同步等待 1-2 分钟,靠提示条安抚,连接断=作废。

### 6. 信息密度浪费

- `listCustomers` 已查回 `tourNo / agent / purchaseDate`,前端表格**没显示**(只有 5 列);
- `modeSummary`(每模式客户数/票数)已加载,页面上只用来算了个总票数,没有可视化。

## 二、定位与北极星

**资料库 = 结算与上家交付之间的交付工作台。**

北极星指标:操作员从"打开资料库"到"确认今天的交付动作"的时间。
三个必答问题,页面首屏直接回答:

1. **有什么可以交付?** —— 按计划(渠道)看待交付客户数
2. **还差什么?** —— 阻断清单(缺字段/未审/需重拍)+ 一键深链去修
3. **发出去了没有?** —— 交付单流水,可重下载、可查客户清单

## 三、三层设计

### ① 数据层:交付单(delivery_runs)

新表(monthly.sqlite,迁移须登记 migration_runner 期望清单——0024 教训):

```sql
CREATE TABLE delivery_runs (
  id            TEXT PRIMARY KEY,          -- run_<stamp>_<rand>
  plan_name     TEXT NOT NULL,             -- 计划名(builtin 用固定名:mode_delivery / lotte_dept / ...)
  plan_kind     TEXT NOT NULL,             -- builtin | dsl | excel
  config_stamp  TEXT NOT NULL,             -- JSON 快照:{planVersion, configMaxStamp}(复核H7,见下)
  scope_json    TEXT NOT NULL,             -- {batchId} | {workspaceKey,modes,dateRange,sinceRunId}
  operator      TEXT NOT NULL,             -- 执行人(重下载 owner 校验锚,复核C1)
  status        TEXT NOT NULL,             -- running | done | failed
  stats_json    TEXT,                      -- {customers,entries,blocked,skipped,copyFailed}
  ledger_watermark_id INTEGER,             -- ⭐增量水位=执行时台账 MAX(daily_receipt_export.id)(复核C2)
  artifact_path TEXT,                      -- 相对工作区目录:交付/<run>/xxx.zip(复核M9:不含 ws 段)
  artifact_size INTEGER,
  error_text    TEXT,
  created_at    TEXT NOT NULL,
  finished_at   TEXT
);
CREATE TABLE delivery_run_customers (      -- 包内客户清单(追溯"这单发了谁"),⭐不作增量水位用
  run_id        TEXT NOT NULL,
  workspace_key TEXT NOT NULL,
  customer_id   TEXT NOT NULL,
  PRIMARY KEY (run_id, workspace_key, customer_id)
);
```

要点:

- **增量水位=台账行级,不是客户级**(复核C2 定语义):台账 `daily_receipt_export.id` 是
  AUTOINCREMENT、写入按 row_hash 幂等(新票=新行=新 id,老票不动)。
  增量 = "有 id > 上次 run 水位的台账行"的客户 → **补票后再结算的客户会正确出现在增量里**。
  **水位按「批次 × 计划」记**(2026-07-16 用户补充拍板"每人每批次处理,不混"):
  上次 run = 同 batchId + 同 plan_name 的最近成功 run,增量只在该批次内判——
  不同操作员/不同批次的水位互不影响,天然对齐 owner 隔离。
  `delivery_run_customers` 只负责"这单发了谁"的追溯,不判增量。
  已知边界:workspace reset / tour-rematch 会删行重插、id 前滚 → 已交付客户会再次进增量,
  **接受**(重匹配后的数据本来就该重交付),UI 在增量清单里标注「此前交付过(run_xxx)」。
- **产物落盘 + 专用下载端点**(复核C1 硬伤修正):产物写到
  `exportRoot/<workspaceKey>/交付/<runId>/`,但**不暴露给共享的 `exports/files` 端点**
  (那两个端点是 `read`=全角色 + 无 owner 过滤,复用=批次级隔离直接作废)。
  重下载走专用 `GET /api/library/delivery-runs/:id/download`:
  校验 `run.operator === req.user.username || canAccessAllOperatorData(req.user)`,路径从 run 行取,
  不接受用户输入路径。已交付流水列表同口径过滤(非 admin/finance 只见自己的 run)。
- **staging 直接建在产物目录**(复核M8):执行器加 `destDir` 参数,staging/zip 直接在
  `exportRoot/.../交付/<runId>/` 下构建,成功即就位(免 tmp→exportRoot 的整包二次拷贝与峰值双倍磁盘),
  失败清理该目录。现有 tmp+cleanup 契约保留给配置台预览通路。
- **保留策略(GC)**:交付产物=整批图的真字节副本(非硬链),必须有回收——
  默认保留 30 天或每计划最近 10 单(取并集),夜间任务清理(夜间备份 job 先例);过期 run 行保留、
  artifact 置空,流水与清单永久可查,只有 zip 不能再下。参数进 .env。(拍板点 6)
- **config_stamp 诚实语义**(复核H7):builtin 计划不 seed 进 config_entries,单一 planVersion
  盖不住;且 builtin 产物实际取决于 store 档案/review_base/mode 多源配置。
  → 盖**双戳**:`planVersion`(DSL/Excel 的 config_entries 版本;builtin 未覆盖时=0)
  + `configMaxStamp`(config_meta 全局变更计数器水位,现成)。对账时"两单之间配置动过没有"看后者。
- **悬死自愈**(复核M11):`status='running'` 超过 30min 由看门狗置 failed+error_text
  (批次悬死看门狗先例);job 内 try/finally 兜底落 failed,别双状态源漂移。
- **铁律不动**:只执行 active 版本计划(草稿只能预览);blocked/collision 硬闸照旧(绝不带病落盘)。

### ② 服务层:计划 = 唯一出口

三个新端点(登录即可读,照 P3c `/api/review-config` 公开端点先例;执行=fieldReview,见拍板点 2):

| 端点 | 作用 |
|---|---|
| `GET /api/library/delivery-plans?batchId=` | **与配置台计划注册表 1:1 同源**(见下)+ 每计划在该批次的水位/徽章数 |
| `POST /api/library/delivery-readiness` | **按需 dry-run 预检**:入参 plan+batchId → 就绪 N / 阻断 M(原因聚合+样本+审核台深链)/ 跳过 K(未审)/ 增量清单 |
| `POST /api/library/delivery-runs` + `GET .../:id` + `GET .../:id/download` | 执行(后台 job)/ 轮询 / 专用下载(owner 校验) |

**计划注册表 1:1 同源**(2026-07-16 用户补充拍板"配置台内置交付包已经分开了,照它处理"):

- 资料库计划卡**不自造名字**,直接吃配置台 `planRowsForList()` 同一来源
  (`config_console_routes.js:264`):内置两条=「内置·多模式四规则」「内置·乐天百货门店双图」
  (各带 rulesSpec 人话规则),加上所有 active 的 DSL/Excel 计划——配置台里是几条、叫什么、
  规则怎么写,资料库就是几张卡、同名同规则,永远不会两边对不上;
- 现资料库 5 按钮里**不在注册表的三个出口收编进 BUILTIN_PLANS 注册**(执行仍走老端点,零改老代码):
  「内置·现代三池交付包」(spec 注明=多模式四规则·规则②的单独出口)、「内置·客户文件夹」、
  「内置·客户数据Excel(每模式一 sheet+需重拍)」——一处注册表管**全部**导出口,
  配置台也因此能看到完整出口清单(元根因"知识写N处"同款解法);
- 该列表函数从 config_console_routes 抽成共享 lib,配置台/资料库两处引用同一实现,不是复制。

**一键全部 + 按渠道单独导出**(2026-07-16 三轮用户需求):

- 「内置·多模式四规则」卡 = **一键交付包**:批次内所有客户按四条分拣规矩自动归位,一次出包;
  卡片文案白话化(planLabel 支持配置台改名,内置默认标签改成
  「一键交付包(全部模式自动分类)」这类人话,"内置/四规则"术语只留在规则详情里);
- 卡下**按"批次内实际出现的模式"自动列子卡**(济州道辉 5 客户 / 新罗V团 4 / 现代 3 / …),
  点谁单独出谁的包——**实现=同一 planner 全量解析后按顶层文件夹切片打包**
  (纯输出过滤,不重写任何分拣规则,零第二真相源;命名/去重与一键全量完全一致,
  因为就是同一次解析的产物子集);
- 切片边界:含 S活动 的模式连带 `S活动/{模式}/` 副本夹一起切;现代=`现代免税店/` 顶层夹;
  空模式客户=「未归类」子卡,按钮不是导出而是「去处理」(深链审核台/账单管理把模式补上);
- 四条规则**不拆成四个独立计划**:它们是一键包内部的分拣规矩,拆开=四份真相;
  "单独发某渠道"的诉求由子卡切片满足。

**每人 × 每批次 = 处理单元**(2026-07-16 用户补充拍板"不要混在一起"):

- 操作员进资料库**必须先选自己的批次**(不提供"全部批次"聚合视图,与"建档必须带批次"的
  批次前置精神一致);选中后,漏斗数字/计划卡待交付数/客户表/阻断/交付流水**全部只算该批次**;
- 每计划徽章 = 该批次内的廉价 SQL(`source_batch_id = ?` 已有过滤,比工作区口径更便宜);
- 交付流水按批次挂:批次选择器每行直接标「已交付 2 单 / 有新增」,一眼看出哪个批次还欠交付;
- admin/finance 的跨批次渠道视图是**单独页签**(P2),与操作员批次视图不共用口径,不混。

**预检成本分层**(复核M10:别把 O(批次×任务) 扫描按卡片数翻倍):

- 计划卡上的徽章 = **廉价 SQL 口径**:已结算且 `id >` 该计划上次水位的客户数(台账一条 GROUP BY,便宜),
  进页面时随 delivery-plans 一次算完(所有计划共享一遍查询);
- 精确的 blocked/skipped = 点「预检」才跑 dry-run(DSL 走 resolveExportPlan;
  builtin 走各自 planner 的 plan 函数——配置台预览同款装配,`config_console_routes.js:582-599`);
- overview 合并端点照旧修 summary/customers 双扫(重拍扫描单遍复用)。

**并发与锁**(复核H6 定规矩):

- 交付 job **不取工作区 pipeline 独占锁**(取了=交付 1-2 分钟内全工作区 settle/import 被阻塞,
  边审边结的日常直接互锁);
- stage_job 幂等键 = `delivery:<planName>:<scopeHash>`(含 batchId/范围,同工作区不同批次不互撞;
  同计划同范围重复点=返回在跑的 job);
- zip 打包过 zip 闸(=2)、xlsx(含包内交付清单构建,复核L13)过 xlsx 闸(=4)——
  后台 job **仍受 semaphore 约束**,在 job 内 acquire,别绕过主线程保护。

**范围(scope)与权限**(复核H3/H4/H5 收口,原设计的"builtin 外层循环合并"**撤回**):

- `{ batchId }`:全计划类型支持,fieldReview 口径(=现状 5 按钮);
- `{ workspaceKey, modes?, dateRange?, sinceRunId? }`:**仅 DSL/Excel 计划**支持,
  且**仅 admin/finance**(跨批次天然跨操作员,reviewer 的 owner 隔离靠批次实现,
  放开=隔离破、不放开=渠道包不完整,两难只有全局角色能解);
- **builtin 保持单批次**:lotte_dept 顶层文件夹带收票日期(`《{收票日期M.D}乐天百货小票》`),
  跨批次合并顶层必分裂——这是上家格式的硬约束,不是实现问题;mode_delivery 的 `_2` 撞名语义
  只在 planner 单批次内生效,外层合并必须重造一遍去重规则 = 第二真相源,踩 2026-07-14 架构裁决红线。
  业务若真需要跨批次 mode_delivery 包,单独立项**改 planner 本身原生吃多批次**(改真相源,带对照测试),
  不做外层缝合。

### ③ 展示层:资料库页面重构(批次优先,2026-07-16 按用户补充拍板改版)

- **左栏=我的批次列表**(owner 过滤,和审核台同口径):每行带 客户数/待交付数/交付状态点
  (● 有欠交付 / ✓ 已交清),哪个批次还欠交付一眼可见;不提供"全部批次"聚合;
- **右栏=选中批次的交付面板**:漏斗/计划卡/三页签全部批次内口径;

- 5 个老按钮过渡期收进「更多(旧版导出)」折叠,P3 下线;
- admin/finance 额外多一个「跨批次(按渠道)」页签(P2),与批次面板分开,不混口径;
- 审核台「确认并结算」成功 toast 加轻量深链「已进资料库,该批次待交付 N」(可选,P2)。

## 四、业务流程(提速点对账)

| 现状动作 | 新流程 | 省掉的 |
|---|---|---|
| 打包 1-2 分钟 → 422 → 回审核台找票 → 再打包 | 预检前置:先看阻断,深链去修,清零再导 | 盲打包循环 |
| 人记"哪个批次发过了" | 行级增量水位:"上次交付后新结算/补票 12 客户",一键导增量 | 漏发/重发风险 + 记忆负担 |
| 一天 N 批次逐个导包手工合并 | DSL/Excel 计划 scope=工作区+模式+日期(admin/finance) | 手工合并 |
| 发没发过靠翻聊天记录 | 已交付流水 + 重下载 + 包内交付清单 | 对账扯皮 |
| 盯着提示条等 zip,不敢关页面 | 后台 job,完成后从已交付页签下载 | 白打包 |

## 五、与配置台的边界(红线)

1. **配置归配置台,执行归资料库**:计划的增删改/版本/冲突检查只在配置台;资料库只读 active 计划+执行。
2. **builtin 不改写、不外层缝合**(复核H5 后收严):跨批次能力只给 DSL/Excel;
   builtin 要跨批次就改 planner 真相源本身,单独立项。
3. **硬闸不放松**:blocked/collision/空产出 → 拒绝执行并列清单,资料库侧只是把清单前置到预检。
4. **存储恒 canonical**:交付形态(带杠/借位)仍是导出层的事,资料库不碰字段口径。
5. **已结算永不回溯**:delivery_runs 只追加;重复交付不拦(业务可能真要重发),卡片明示"该范围已交付过"。
6. **owner 隔离是一等约束**(复核C1 后补):交付产物列表/下载/流水全部按 operator 过滤,
   绝不复用无 owner 过滤的共享 `exports/files` 端点。

## 七、拍板结果(2026-07-16 用户已拍板)

**用户拍板三点(均取推荐项)**:

1. ✅ **补票重发**:客户交付后补票再结算 → 下次导出**重新进包**(全部票含新票),界面标注「之前发过」。
   → 增量水位=台账行级 `ledger_watermark_id` 定稿;reset/重匹配后重进增量同口径。
2. ✅ **跨批次权限**:跨批次渠道包**仅 admin/finance**;普通操作员照旧按自己批次导,隔离不破。
3. ✅ **builtin 不合包**:交付包(按模式)/乐天百货包维持单批次;跨批次合包能力只给新配置的 DSL/Excel 计划。
   业务将来真需要 mode_delivery 合包再单独立项改 planner 真相源。

**用户补充拍板两点(2026-07-16 二轮)**:

4. ✅ **计划卡与配置台注册表 1:1 同源**:配置台里内置交付包已拆成独立计划
   (「内置·多模式四规则」/「内置·乐天百货门店双图」,`config_console_routes.js:254-257`),
   资料库照这个注册表出卡,不自造名字;老 5 按钮里不在注册表的三个出口(现代三池/客户文件夹/
   客户数据Excel)收编进 BUILTIN_PLANS 注册(执行仍走老端点);列表函数抽共享 lib 两处引用。
5. ✅ **资料库以「每人 × 每批次」为处理单元,不混**:操作员必须先选自己的批次,
   漏斗/卡片/客户表/流水全部批次内口径;不提供跨批次聚合视图;增量水位按 批次×计划 记;
   admin/finance 的跨批次渠道视图是独立页签(P2),与批次面板不共用口径。

**用户补充需求(2026-07-16 三轮)**:

6. ✅ **一键全部 + 单渠道子卡**:保留"一键交付包"(全部模式自动分类);
   卡下按批次内实际模式列子卡,点谁单独出谁(同一 planner 解析后按顶层文件夹切片,
   不拆四规则、不重写规则);未归类子卡=「去处理」深链;内置计划标签改白话
   (「一键交付包(全部模式自动分类)」),"内置/四规则"术语只留规则详情。

**其余四项按推荐默认执行**(实现细节,用户可随时改):
计划卡默认导增量+一键切全量;导出全部转后台 job+完成自动触发下载;
老 5 按钮 P0 保留原位 → P1 收进「更多」折叠 → P3 下线;

## 八、architect 复核结论(2026-07-16,已全部并入正文)

- **C1 交付产物下载零 owner 隔离**(复用 exports/files 会绕过批次级隔离)→ 专用下载端点+operator 校验,红线第 6 条。
- **C2 增量水位选错载体**(客户 membership 抓不到补票)→ 行级水位 `ledger_watermark_id`,
  delivery_run_customers 降级为追溯清单。
- **H3 跨批次×owner 隔离冲突** → 跨批次仅 admin/finance,拍板点 2。
- **H4 lotte 顶层日期文件夹跨批次必分裂** → lotte 永远单批次(上家格式硬约束)。
- **H5 builtin 外层合并=第二真相源** → 撤回外层循环方案,跨批次只给 DSL/Excel;
  builtin 跨批次=改 planner 真相源,单独立项。
- **H6 锁粒度/semaphore 绕过** → 不取 pipeline 锁、stage 键含 scope、job 内过 zip/xlsx 闸。
- **H7 builtin configVersion 空锚** → 双戳 {planVersion, configMaxStamp},诚实语义。
- **M8 磁盘膨胀无 GC** → staging 直建产物目录(免双写)+保留策略拍板点 6。
- **M9 artifact_path 相对基准错** → 改为相对工作区目录(且不走共享端点)。
- **M10 readiness 全批扫描×卡片数** → 徽章=廉价 SQL,dry-run 按需。
- **M11 running 悬死无 reaper** → 30min 看门狗+try/finally 兜底。
- **L12/L13** → 专用端点后 L12 大体消解;交付清单 xlsx 纳入 xlsx 闸。
