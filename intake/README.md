# Intake · 收票中台

> 把微信免税挂团群里**混乱的消息流**，自动收口成**干净的客户档案**（护照 + 小票 + 行程 + 金额），再喂给已有的 `sign` 对账返点系统。

`intake → sign`：本项目是前端的智能采集与归组层，`sign` 是后端的账单匹配与返点核算层。

## 这是什么

韩国免税挂团返点业务中，代理、客户、财务都在微信大群里沟通。代理用**各式各样、不固定**的方式在群里发客户的护照、小票、行程截图。本系统：

1. **采集** 群消息与图片（企业微信会话内容存档为主）
2. **理解** 用多模态大模型把不固定的消息归一化成标准业务事件
3. **归组** 以护照号为主键，把散落的护照/小票/行程串成一个客户组
4. **编排** 用状态机跟踪每本护照的全生命周期（挂团→购物→交票→对账→返点）
5. **对接** 把结构化结果交给 `sign` 完成对账

## 关键事实

- **规模**：404 个群 / 213 个代理 / 3 类群（业务群 279、沟通群 93、点位群 32）
- **主键**：护照号（一本护照可挂 SG/H/PKG 多个团号）
- **数据源**：企业微信会话内容存档 API（合规、跑 Linux、无单独采集机）
- **真值集**：`ticket/data_sample/` 下 385 个已整理的客户文件夹，用于离线验证
- **技术栈**：Node.js（对齐 sign）+ PostgreSQL + Redis + OSS + 阿里云百炼（Qwen）

## 与 sign 的边界

- `intake` **只写自己的库**，通过约定的数据契约把结果交给 `sign`，不直接改 `sign` 的表。
- 两个项目独立部署、独立迭代，同 VPC 内网互通。
- **本项目不在 `ticket/` 目录下写任何文件。**
