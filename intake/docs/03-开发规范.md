# 03 · 开发规范

> 本规范在全局 ECC 规则基础上，落地为 Intake 项目的具体约定。冲突时以本文件为准。

## 一、技术基线

- 主语言 **Node.js**（与 sign 一致的版本与包管理器，进场前确认 sign 的 `package.json`）。
- 采集器若用 wxauto，单独 Python 进程，**不与主服务混代码库**，只通过 HTTP + 统一消息格式交互。
- 数据库 PostgreSQL；缓存/队列 Redis；对象存储 OSS。

## 二、目录与文件组织

- 按**功能/领域**组织，不按文件类型堆放（见 [02 规划目录结构](02-架构与技术栈.md)）。
- 多个小文件 > 少数大文件：**单文件 ≤ 800 行**，典型 200–400 行；超了就拆模块。
- 数据访问统一走 **仓储模式**（`repositories/`），业务逻辑依赖接口而非具体存储，便于测试与替换。

## 三、编码风格

- **不可变优先**：返回新对象，不就地修改入参；避免隐藏副作用。
- **函数聚焦**：单函数 ≤ 50 行；嵌套 ≤ 4 层，多用提前返回。
- **错误处理显式**：每一层显式处理，绝不静默吞错；面向 UI/审核端给友好信息，服务端记详细上下文。
- **边界校验**：所有外部输入（采集消息、LLM 输出、API 入参、文件内容）在系统边界用 schema 校验；快速失败。
- **无硬编码**：店铺/团种/截止日/路径/密钥等用配置或常量，不散落字面量。

## 四、命名规范

- 文件/模块：kebab-case（`wecom-archive-adapter.js`）。
- 变量/函数：camelCase；类/构造器：PascalCase；常量：UPPER_SNAKE。
- 业务术语统一英文键：`passportNo`、`groupNo`、`receiptNo`、`flightNo`、`store`、`mode`（SG/H/PKG…）。中英对照维护在 `config/` 字典里，避免同义词漂移。

## 五、LLM 调用规范（本项目特有，重点）

1. **输出强约束**：所有抽取/分类必须传 JSON Schema，校验通过才入库；不通过按低置信处理。
2. **必带置信度**：每条抽取结果含 `confidence`；低于阈值进审核队列，绝不静默自动入库。
3. **Prompt 版本化**：prompt 存 `prompts/`，带版本号；事件流水记录所用 prompt 版本 + 模型名，便于重放与回归。
4. **成本与延迟日志**：每次调用记录 token 用量、模型、耗时、命中漏斗哪一级；用于持续优化成本。
5. **漏斗纪律**：能用规则/MRZ 解决的绝不调贵模型；多模态只跑候选图。
6. **重试与降级**：API 失败指数退避重试；连续失败落队列不丢消息。
7. **可重放**：原始消息 + prompt 版本不变，改进后可对历史重跑对比准确率。
8. **审核回流**：人工修正结果沉淀为标注样本，定期纳入 few-shot / 回归集。

## 六、测试规范

- **TDD**：先写测试（RED）→ 最小实现（GREEN）→ 重构（IMPROVE）。
- **覆盖率 ≥ 80%**。
- 三类测试：
  - **单元**：MRZ 解析、团号正则、分组连接逻辑、状态机转移、金额解析。
  - **集成**：采集→落库→抽取→事件→入库链路；仓储读写。
  - **离线验证（本项目核心）**：以 385 文件夹为回归集，跑出抽取准确率 / 分组准确率 / 成本，作为每次 prompt 或规则变更的守门指标。
- LLM 相关测试用**固定样本 + 录制响应**，避免每次真调 API 抖动；准确率回归单独用真实样本批量跑。

## 七、Git 规范

- 约定式提交：`<类型>: <描述>`，类型 feat/fix/refactor/docs/test/chore/perf/ci。
- 提交信息说清"做了什么 + 为什么"。
- 不在默认分支直接改，先开分支；提交/推送仅在用户要求时进行。
- **绝不提交密钥/私钥/护照图/真实客户数据**；见 [04 合规规范](04-合规与数据安全规范.md) 与 `.gitignore`。

## 八、配置与密钥

- 所有密钥（百炼 AK/SK、企微 corpid/secret、RSA 私钥、数据库口令）走环境变量或阿里云密钥管理，**不入代码、不入 git**。
- 启动时校验必需密钥存在，缺失快速失败并明确报错。
- 配置（404 群表、规则字典、阈值）与代码分离，可热更新优先。

## 九、日志与可观测

- 结构化日志（JSON），含 trace id 贯穿一条消息全链路。
- 关键指标：消息吞吐、漏斗各级命中率、抽取置信度分布、审核队列长度、API 成本、企微拉取 seq 落后量。
- 敏感字段（护照号、姓名）日志中**脱敏**。

## 十、代码审查（按 ECC 主动派发）

- 写完/改完一段代码 → 立即 **code-reviewer**（Node/JS 用对应 reviewer）。
- 涉及认证、密钥、护照 PII、外部 API、SQL → 提交前 **security-reviewer**。
- 新需求/复杂功能/重构 → 先 **planner**；修 bug/加功能 → **tdd-guide** 先测试。
- 构建/类型/依赖报错 → 对应 **build-resolver**。
- 审查严重级别：CRITICAL 阻止合并；HIGH 应修；MEDIUM 考虑；LOW 可选。

## 十一、完成前检查清单

- [ ] 函数 <50 行、文件 <800 行、嵌套 <4 层
- [ ] 不可变、无硬编码、错误显式处理、边界校验
- [ ] LLM 输出有 schema 校验 + 置信度 + 成本日志
- [ ] 测试覆盖 ≥80%，385 离线回归未下降
- [ ] 无密钥/PII 入库入 git，敏感日志脱敏
- [ ] 已过相应 reviewer（含 security-reviewer 若触发）
